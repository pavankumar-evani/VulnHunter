## Findings (most severe first)

### VULN-1 — Hardcoded Stripe API key — **CRITICAL** (CWE-798)
**File:** `app.py:22`
An attacker who reads the source (or pulls the Docker image) gets a live-looking Stripe
secret key directly, no exfiltration needed. If real, this key could be used to move
money or read the entire Stripe account's transaction history.
```
STRIPE_API_KEY = "sk_live_DEMO_FAKE_NOT_A_REAL_KEY_1234567890"
```
**Fix:** load from `os.environ["STRIPE_API_KEY"]`; never commit real keys.

### VULN-2 — SQL Injection via string concatenation — **CRITICAL** (CWE-89)
**File:** `app.py:37`
The `id` query parameter is concatenated directly into SQL. `?id=1 OR 1=1` dumps every
user; `?id=1; DROP TABLE users;--` (driver-permitting) destroys data. An attacker can read
or corrupt the entire `users` table with a single crafted URL.
```
query = "SELECT id, username, email FROM users WHERE id = " + user_id
```
**Fix:** parameterized query — `cursor.execute("SELECT ... WHERE id = ?", (user_id,))`.

### VULN-4 — Command injection via `shell=True` — **CRITICAL** (CWE-78)
**File:** `app.py:58`
`host` is attacker-controlled and passed straight into a shell command. A value like
`127.0.0.1; cat /etc/passwd` runs arbitrary shell commands on the host with the
application's privileges.
```
output = subprocess.check_output(f"ping -c 1 {host}", shell=True)
```
**Fix:** pass args as a list with `shell=False`: `subprocess.check_output(["ping", "-c", "1", host])`.

### VULN-8 — Secret baked into Docker image layer — **CRITICAL** (CWE-798)
**File:** `Dockerfile:12`
`ENV STRIPE_API_KEY=...` bakes the secret into every image layer — anyone with `docker
history`/pull access to the image gets the key even after it's "removed" from a later
layer.
**Fix:** remove the `ENV` line; inject the secret at container runtime (`docker run -e
STRIPE_API_KEY=...` or a secrets manager), never at build time.

### VULN-3 — `eval()` on untrusted input — **HIGH** (CWE-95)
**File:** `app.py:50`
`/calc?expr=...` evaluates arbitrary Python. `expr=__import__('os').system('whoami')`
executes arbitrary code on the server.
**Why not auto-fixed:** the endpoint's actual purpose is evaluating arbitrary arithmetic
expressions — swapping in `ast.literal_eval` would silently break it (it only parses
literals, not expressions like `2+2`). Replacing `eval` safely needs a real expression
parser/allow-list, which is a design decision, not a mechanical edit.

### VULN-6 — Plaintext password storage — **HIGH** (CWE-256)
**File:** `app.py:63-72`
Passwords are stored exactly as submitted. A database leak (or an insider) exposes every
user's real password immediately, and since people reuse passwords, that risk extends to
their other accounts too.
**Why not auto-fixed:** switching to hashed passwords (e.g.
`werkzeug.security.generate_password_hash`) changes the storage format — existing rows
would need a migration/re-registration plan, which is a product decision, not a
same-behavior mechanical fix.

### VULN-5 — Debug mode enabled in entrypoint — **MEDIUM** (CWE-489)
**File:** `app.py:90`
`debug=True` in `app.run()` enables Werkzeug's interactive debugger, which lets anyone
who can trigger an unhandled exception execute arbitrary Python in-process — a full
remote code execution path if this ever runs with production-like network exposure.
**Fix:** gate behind an environment variable defaulting to `False`.

### VULN-7 — Container runs as root — **MEDIUM** (CWE-250)
**File:** `Dockerfile`
No `USER` instruction means the process runs as root inside the container. A container
escape or dependency RCE then hands the attacker root, not a limited account.
**Fix:** add a non-root `USER` after `pip install`.

### VULN-9 — Unpinned/outdated base image — **LOW**
**File:** `Dockerfile:7`
`FROM python:3.9` (no patch digest) pulls whatever the tag currently resolves to, and
3.9 is an old minor version — likely carrying known, patched CVEs in the base OS/Python
runtime. Verify against a CVE database before treating this as confirmed.
**Why not auto-fixed:** bumping the base image can change behavior; needs a human to
verify compatibility.
