1. Introduction

VulnHunter is two things sharing one repository: a pair of Claude Code subagent pipelines (“/vulnhunt” for source-code scanning, “/remediate” for infrastructure-finding remediation), and a full FastAPI + vanilla-JS dashboard application that reads and drives them. This guide is for anyone who needs to work in the codebase directly — a new developer, a contractor, or the product's own owner returning after time away — covering how to get the code, run it, test it, extend it, and the git conventions this specific repository follows.

It assumes basic familiarity with git, Python, and the command line. It does not replace the deeper reference material this repo already ships — §10 points to each of those documents by name.

2. Getting the code

The canonical repository lives on GitHub:

https://github.com/pavankumar-evani/VulnHunter

Clone it and check out the trunk branch, which is master:

git clone https://github.com/pavankumar-evani/VulnHunter.git
cd VulnHunter

2.1 Working across multiple sessions in parallel

This repository is regularly worked on by more than one Claude Code session at once, each in its own git worktree — a second working directory attached to the same repository, on its own branch, without needing a second clone:

git worktree add ../vulnhunter-feature-x -b feature-x
git worktree list          # see every active worktree
git worktree remove ../vulnhunter-feature-x   # after merging
Before pushing

Always git fetch origin master and check for divergence before pushing to master — with more than one session or contributor active, origin/master moves. On a non-fast-forward rejection, fetch and inspect what changed (git show / git diff) before merging; don't force-push.

4. Running the application locally

  1. Install the dashboard's dependencies: pip install -r dashboard/requirements.txt
  2. Start the server: python dashboard/app.py
  3. Open https://127.0.0.1:5050 in a browser.
HTTPS is on by default

The first run auto-generates a local self-signed certificate into dashboard/certs/ and serves HTTPS from then on — your browser will show a one-time “not private” warning, which is expected for a self-signed cert. Click through it (Advanced → Proceed in Chrome/Edge), or install dashboard/certs/cert.pem into your OS's trusted-root store once to make the warning disappear permanently. Set VULNHUNTER_DISABLE_TLS=true before running the command above to fall back to plain HTTP instead.

Two seed accounts ship with the repository (see dashboard/auth/users.json) so the app is usable immediately:

EmailPasswordRole
admin@vulnhunter.localChangeMe123!Admin
analyst@vulnhunter.localChangeMe123!User

These are intentionally public demo credentials, documented in the repo itself — change or remove them (same users.json file, or a real user record once auth/users.json is replaced with real accounts) before any deployment a real customer will reach.

5. Running the two pipelines

5.1 Interactively, inside Claude Code

claude
/vulnhunt <path-to-target-repo> [--fix]
/vulnhunt vulnerable-demo-app --fix
/vulnhunt vulnerable-demo-app --verify VULN-2 vulnhunter/auto-fixes-<branch>
/remediate                     # ingests remediation/sample-data/* by default
/remediate --generate          # also generates Ansible playbooks

5.2 Headless — CI, cron, or the dashboard's own Run Pipeline page

python cli/vulnhunter.py --dry-run scan vulnerable-demo-app --fix   # preview only, no spend
python cli/vulnhunter.py scan vulnerable-demo-app --fix             # real run, spends API usage
python cli/vulnhunter.py --dry-run remediate --generate
python cli/vulnhunter.py remediate --generate

The dashboard's own /run page is a thin UI over this exact same entry point — same dry-run default, same confirm gate, same budget cap (default $2.00, admin-adjustable up to $500).

6. Testing

python -m unittest discover -s tests -p "test_*.py"    # everything — 1,458 tests today
python -m unittest tests.test_dashboard -v               # dashboard API + auth-gating tests
python -m unittest tests.test_auth -v                     # passwords/sessions/users/OIDC

GitHub Actions (.github/workflows/ci.yml) runs the full suite on every push and pull request. For JavaScript, node --check <file> only catches syntax errors — it will not catch a missing import, which only surfaces as a runtime error in the browser. Reload the actual page and check the console before calling a frontend change done.

7. Git workflow conventions

  • Branch off master for any real change; name the branch for what it does (fix-, feature-, or a short slug — this repo doesn't enforce a strict prefix, but a descriptive name beats a ticket number nobody else can look up).
  • Commit messages lead with what changed and, in the body, why — not a restatement of the diff. Two real examples from this repo's own history:
Fix /api/status reporting a not-yet-created store as existing when
checked after activity_log

Make Chakra Petch the app's primary font, not just the login page's

Scoped to .auth-hero-brand/.auth-hero-tagline/.login-brand before - now
the single body-level font-family (everything else inherits it) so the
same typeface carries through the sidebar, every dashboard, and every
data table.
  • Stage specific files by name, not git add -A — review git status before committing so a stray .env or credential file never lands in a commit.
  • Open a pull request with the gh CLI: gh pr create --title "..." --body "..." — summarize what changed and how it was tested, not a restatement of the title.
  • Never force-push to master, and never amend a commit that's already been pushed — create a new commit instead.
  • Run the full test suite before opening a PR, and again on the merged tree if you had to resolve a conflict — two branches can each be individually correct and still not verified together.

8. Extending the product

8.1 Adding a new connector

Every pull connector follows one small contract:

class SomeConnector:
    def __init__(self, ...credentials..., session=None):
        self.session = session or requests.Session()   # DI seam for tests

    def test_connection(self):
        """Cheapest real authenticated call - no confirm gate needed."""

    def fetch_and_write_csv(self, output_path):
        """Real fetch, confirm-gated at the route level, never here."""
  1. Write remediation/connectors/<name>_connector.py against the vendor's real, public API.
  2. Decide the output shape: flatten into tenable_connector.CSV_FIELDNAMES (CVE-scoped host source), normalize directly to the Finding schema (already-typed posture source), or the asset-inventory shape.
  3. Unit-test against a hand-rolled fake object, not the vendor SDK's own mocks.
  4. Add POST /api/<name>/test-connection (admin-gated, no confirm) and POST /api/<name>/fetch (confirm-gated).
  5. Wire api.js, a page module under pages/, and an app.js router entry.
  6. Disclose the real verification status in the module docstring and the dashboard page — “built against public docs, unit-tested against mocked responses, never exercised against a real account” is the default and expected state for a new connector.

8.2 Adding a new remediation fixer

The one rule that's never relaxed

Any subagent that drafts a change to real infrastructure config gets Read, Write tools only — never Bash, never a network tool, never stored credentials. This is what makes “nothing in this repository ever executes against real infrastructure automatically” true by construction rather than by policy, and it applies to every fixer subagent without exception.

9. The subagent safety model

Every subagent's tools: list in its own YAML frontmatter is a hard boundary, not a suggestion — the actual enforcement mechanism, not a runtime check the agent could talk its way around.

SubagentToolsWhy
vuln-scannerRead, Grep, Glob, BashNo Edit/Write — physically cannot modify what it's scanning
vuln-triage-reporterWriteProduces a report only — cannot scan or fix
vuln-fixerRead, Edit, Write, BashNew-branch-only git workflow; never commits to master
vuln-verifierRead, Grep, Glob, BashRe-checks a fix via git show/git grep against a named branch; never checks it out
remediation-fixer-windows / -unixRead, WriteDrafts a playbook; cannot run one — no Bash, no network
remediation-fixer-otRead, WriteCompensating-control recommendation only, never a patch script
remediation-fixer-applicationRead, WriteDependency-upgrade plan only; cannot edit a manifest or run a package manager
