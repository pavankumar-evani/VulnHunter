1. How to use this guide

This guide prices out everything needed to run VulnHunter as a real, commercially-hosted product: the application infrastructure itself (compute, database, storage, networking, TLS, a firewall/WAF, DNS), the licenses the software stack requires (there are none that cost money — see §9), and the business-side services a paying product needs on top of the code (a support desk, a documentation/community portal, a marketing site, and the basic legal/financial scaffolding of a company that can accept payment).

Every dollar figure below comes from each vendor's own public pricing page or pricing API, checked in September 2026, and is labeled with what it covers. Cloud pricing changes — sometimes with very little notice, as several of the callouts below show — so treat every number here as a planning estimate, not a quote, and re-check the vendor's own calculator before committing budget. Two things are deliberately excluded from every total in this guide, called out again in §18: outbound data-transfer (egress) charges, which depend on real traffic volume this guide has no way to predict, and any vendor's promotional first-year discount, since those expire and this guide prices what the service actually costs to run.

⚠ Read this before budgeting

Wherever a number in this guide could not be verified against a real, current, public source — most notably Oracle Cloud's own database pricing in §7.2 — it is called out explicitly, in the same amber box as this one, rather than filled in with a guess. Section 18 collects every one of those gaps in a single checklist.

2. What you're actually deploying

VulnHunter's dashboard is one FastAPI process (Python) serving a JSON API and a hand-rolled vanilla-JS single-page app — no message queue, cache layer, or microservice boundary to provision. It talks to a local SQLite database today, accessed through SQLAlchemy Core specifically so that moving to a real managed Postgres database for production is a connection-string change, not a rewrite. That's the one architecture change every deployment in this guide makes: point the app at a managed PostgreSQL instance instead of the local SQLite file, so the database survives an instance restart or redeploy and can be backed up and scaled independently of the app.

Beyond the app and its database, a real deployment needs: persistent storage for generated artifacts and logs; a load balancer terminating TLS in front of the app (uvicorn's own built-in TLS, used today for local development, is not what should face the public internet); a Web Application Firewall in front of that; a registered domain with DNS pointed at the load balancer; outbound email for the notification scheduler's alerts; and network/firewall rules that allow exactly the traffic the app needs and nothing else (§ Network & firewall in each cloud section gives the concrete rule set). If either pipeline is triggered from the dashboard's own Run Pipeline page in production, the host running the dashboard also needs the Claude Code CLI installed and its own API credentials — that spend is metered separately by Anthropic, not by the cloud host, and is not part of any figure in this guide.

5. Amazon Web Services

The most mature option of the four, with the deepest managed-service catalog and the largest ecosystem of Ansible/Terraform tooling already available if VulnHunter's own remediation-fixer playbooks need a reference target.

5.1 Compute

Run the FastAPI app on EC2, behind the load balancer described in §5.4 — not directly exposed to the internet. A single instance is enough through the Mid tier; Large should run at least two instances behind the load balancer for availability, not just capacity.

Amazon RDS for PostgreSQL. This is the connection-string change described in §2 — point SQLAlchemy at the RDS endpoint instead of the local SQLite file.

TierConfigurationCost

5.3 Storage

EBS gp3 for the instance's own disk (generated Ansible playbooks, logs, the local artifact tree) plus S3 for durable backups of the database and those same artifacts. At Pilot scale this is a small line item — roughly $4/mo for 20 GB of gp3 plus incidental S3 backup storage — that grows with retention policy and artifact volume rather than asset count directly.

5.4 Load balancing & TLS

An Application Load Balancer (ALB) terminating TLS with a free AWS Certificate Manager (ACM) certificate, forwarding to the EC2 instance(s) on the app's port. This replaces uvicorn's own self-signed development certificate for any real deployment.

ComponentPilot cost
Application Load Balancer + ACM certificate$22.27 / mo

5.5 Web Application Firewall

AWS WAF attached to the ALB, with a managed rule group (e.g. the Core Rule Set) covering common injection and bot patterns before traffic reaches the app.

ComponentPilot cost
AWS WAF, one Web ACL + managed rule group$12.60 / mo

5.6 DNS & domain

Route 53 hosts the DNS zone ($0.90/mo for the hosted zone at Pilot scale) regardless of where the domain itself was registered — see §10 for registrar comparison, including Route 53 Domains as one of the options.

5.7 Network & firewall rules

A VPC with a public subnet (load balancer only) and a private subnet (app instances and the RDS database, no direct internet route). Concrete security-group rules:

  • Inbound to the ALB: TCP 443 from 0.0.0.0/0 (and only from there — nothing else in the VPC accepts a public inbound connection).
  • Inbound to the app instance(s): TCP 8000 (or whatever port the app listens on) from the ALB's security group only.
  • Inbound to RDS: TCP 5432 from the app instances' security group only — never from 0.0.0.0/0.
  • Outbound from the app instance(s): HTTPS to CISA's KEV feed and FIRST.org's EPSS API (threat-intel enrichment), to api.anthropic.com if the dashboard triggers a pipeline run, and to github.com/api.github.com if vuln-fixer pushes a branch. Deny outbound by default and allow these explicitly rather than opening all outbound traffic.
  • SSH/admin access: no open port 22 to 0.0.0.0/0 — use AWS Systems Manager Session Manager (no inbound port needed at all) or restrict TCP 22 to a specific admin IP range.

5.8 Outbound email

Amazon SES for the notification scheduler's outbound alerts — $0.05/mo at Pilot scale (SES bills per message sent, so this line grows with alert volume, not asset count).

5.9 Free tier & startup credits

AWS restructured its free tier on July 15, 2025: new accounts now get up to $200 in credit over their first 6 months, replacing the older “12 months free” model — plan for that credit to run out well before Pilot-tier revenue does. Separately, AWS Activate (for genuinely new companies) offers $1,000–$5,000 in the self-serve Founders tier, and up to $200,000 for companies backed by a participating VC or accelerator (Portfolio tier) — worth applying for regardless of which cloud is chosen for production, since Activate credit can be used to offset the AWS bill specifically.

5.10 Provisioning checklist

  1. Create the VPC (public + private subnets) and security groups from §5.7.
  2. Launch the RDS PostgreSQL instance in the private subnet; note its endpoint.
  3. Point the app's database connection string at the RDS endpoint instead of the local SQLite file; run any pending migrations.
  4. Launch the EC2 instance(s) in the private subnet; deploy the app; confirm it's reachable only from inside the VPC so far.
  5. Request or import an ACM certificate for the domain; create the ALB in the public subnet with an HTTPS listener using that certificate; target the app instance(s).
  6. Create a WAF Web ACL with a managed rule group; associate it with the ALB.
  7. Create the Route 53 hosted zone; point the domain's nameservers at it (or, if the domain is registered elsewhere, add the NS records there); create an A/ALIAS record for the domain pointing at the ALB.
  8. Verify a sending domain/address in SES and request production access (new SES accounts start in a sending-limited sandbox).
  9. Set VULNHUNTER_SESSION_SECRET to a real, stable value before pointing real users at the deployment.

6.6 Provisioning checklist

  1. Create the VNet with app and database subnets, and the NSGs from §6.4.
  2. Provision the PostgreSQL Flexible Server in the database subnet; point the app's connection string at it.
  3. Create the App Service Plan and deploy the app, restricted to the app subnet via VNet integration.
  4. Decide on the WAF question in the callout above; provision Application Gateway (with WAF_v2 if justified) or a plain Standard Load Balancer with a separately-managed TLS certificate if not.
  5. Create the Azure DNS zone, delegate the domain's nameservers to it (or add equivalent records at the existing registrar), and point the domain at the Application Gateway/Load Balancer's public IP.
  6. Set VULNHUNTER_SESSION_SECRET before real traffic arrives.

7.5 Provisioning checklist

  3. Provision the database service confirmed in step 1; point the app's connection string at it.
  4. Launch the compute instance(s) — Always Free Ampere A1 (sized to the current 2 OCPU / 12 GB ceiling) for Pilot, a paid shape for Mid/Large — and deploy the app.
  5. Provision the Load Balancer with a TLS certificate and the Web Application Firewall service in front of it.
  6. Point the domain at the Load Balancer via OCI DNS or the existing registrar.

8. Budget-friendly alternative: DigitalOcean

Of the lower-cost providers checked for this guide, DigitalOcean came out as the most complete budget option — a real managed Postgres product and a real load balancer, which not every low-cost provider offers. Two comparable alternatives are worth naming directly: Vultr prices its equivalent droplets identically to DigitalOcean ($24/mo and $48/mo tiers), and Hetzner — historically the standout budget option — is no longer dramatically cheaper after four price increases through 2026 that cumulatively raised its CPX line roughly 225%; its comparable instance now runs about $22.61/mo against DigitalOcean's $24, which is closer to parity than a meaningful discount.

DigitalOcean Cloud Firewalls, scoped the same way as every other cloud in this guide: public HTTPS only at the load balancer (or at Cloudflare, if proxying through it), database access restricted to the droplet's private network, no public admin port (use DigitalOcean's console access instead of exposing SSH, or restrict it to a specific admin IP), outbound restricted to the KEV/EPSS feeds, api.anthropic.com, and GitHub.

8.3 Provisioning checklist

  1. Create the Droplet and the Managed PostgreSQL cluster in the same region/VPC; point the app's connection string at the managed database.
  2. Create the Load Balancer with a Let's Encrypt certificate (DigitalOcean provisions and renews this automatically) targeting the Droplet.
  3. If using Cloudflare as a WAF substitute, proxy the domain through Cloudflare and enable its WAF ruleset, pointing Cloudflare's origin record at the Load Balancer.
  4. Configure the Cloud Firewall rules from §8.2.
  5. Set VULNHUNTER_SESSION_SECRET before real traffic arrives.

9. Licenses required

None of VulnHunter's own software stack carries a license fee. Every component is permissively licensed open-source software, safe to use in a commercial, closed-source product without royalty:

ComponentLicenseCommercial-use note
Python, FastAPI, Starlette, UvicornPSF / MIT / BSDNo fee, no attribution requirement in the shipped product.
SQLAlchemyMITNo fee.
PostgreSQLThe PostgreSQL License (permissive, similar to MIT)No fee, no restriction on commercial or SaaS use.
SQLite (local/dev use)Public domainNo fee.
Chakra Petch (typeface)SIL Open Font License 1.1No fee; may be embedded in the product and in generated documents. May not be sold on its own as a font product, which VulnHunter does not do.

The one recurring “license-shaped” cost some buyers expect is a paid TLS certificate from a commercial certificate authority — this is not actually required. Let's Encrypt issues the same trust-level certificate for $0, automatically renewed, and is what most of the checklists above already assume. A paid CA certificate (roughly $99–217/yr where offered) buys a vendor logo and a support contract, not stronger encryption, and is a procurement-checklist item for certain enterprise buyers rather than a technical necessity — see §13 for the current industry-wide certificate-lifetime change that applies regardless of which CA is used.

17. Recommended path by growth stage

Pilot / pre-revenue

Azure without a WAF, or DigitalOcean, for the lowest fixed cost while proving the product with a design partner. Let's Encrypt (already the default), Help Scout's free support tier, Docusaurus on Cloudflare Pages for docs, and Wyoming for the entity if self-filing. Apply for cloud startup credits (AWS Activate or Microsoft for Startups) regardless — free runway either way.

Mid / early paying customers

Move to AWS or Azure with a WAF now in place — the fixed WAF cost becomes proportionate once real customer traffic and the first compliance questionnaires arrive. Upgrade the database to Multi-AZ. Move support to Freshdesk Growth once the team outgrows Help Scout's 5-user free tier. Consider GitBook or ReadMe.com for docs if a non-technical team member now owns that content.

Large / enterprise scale

AWS or Azure with full Multi-AZ/HA and a WAF are the only two options modeled at this tier in this guide — OCI and DigitalOcean's own figures don't extend cleanly to 25,000+ assets without a fresh quote. Formalize cyber/tech E&O insurance if it isn't already in place; move to Chargebee or Paddle for billing if usage-based pricing or multi-jurisdiction tax handling is now needed; Zendesk Suite Professional if an enterprise buyer specifically requires it during procurement.

18. What to verify before you commit

Collected in one place — every figure in this guide that is a planning estimate rather than a locked-in quote:

  • OCI managed-database pricing (§7.2) — not published anywhere this research could reach; get a live quote from OCI's own Cost Estimator before treating any OCI total as comparable to AWS/Azure/DigitalOcean.
  • Data-transfer/egress charges — excluded from every total in §4–§8 on every cloud, because they depend on real traffic volume this guide has no way to predict. Model this once there's real usage data, not before.
  • Namecheap's actual renewal-year domain price (§10) — its promotional first-year rate could not be verified against a stable published renewal price.
  • Document360 pricing (§12) — no longer publicly published; requires a sales quote.
  • Cyber/tech E&O insurance (§15.3) — fundamentally quote-driven; the range given is a planning ballpark, not a price.
  • Every cloud vendor's promotional or startup-credit pricing (§5.9, §6.5) — credits expire and Activate/Founders Hub award amounts are awarded case-by-case, not guaranteed at the figures quoted.

Appendix A: Network & firewall rule reference

The same five rules apply on every cloud in this guide — only the product name implementing each one changes:

RuleImplemented as
Public HTTPS only at the edgeALB (AWS) / Application Gateway (Azure) / Load Balancer (OCI, DigitalOcean) — the only thing with a public inbound rule on port 443.
App reachable only from the edgeSecurity group / NSG / security list rule scoping the app's port to the load balancer's own security group — never to 0.0.0.0/0.
Database reachable only from the appSecurity group / NSG rule scoping the database port (5432 for Postgres) to the app tier's security group — never public.
No public admin portSystems Manager Session Manager (AWS) or an equivalent console-based access method instead of exposing SSH/RDP; if SSH must stay open, restrict it to a specific admin IP range.
Outbound allow-list, not allow-allKEV/EPSS threat-intel feeds, api.anthropic.com (if pipelines run from this host), and github.com/api.github.com (if vuln-fixer pushes branches) — deny everything else outbound by default.
