SOC, Threat Hunting & Detection Engineering

How Quanta takes an alert from arrival to a closed case, how every report is generated, which statistical models sit behind the recommendations, and exactly which parts are fixed rules, classical statistics, or an optional language model. Every claim here traces to a module in remediation/hunting/, remediation/soc/ or remediation/soar/ and a threshold in a YAML file you can read.

The short version

Nothing in the investigation, case, hunt or detection tooling is a black box. Verdicts are weighted scores of named signals; reports are assembled from data Quanta holds, never written by a model; the TTP classifier is Naive Bayes you can inspect; the playbook recommender is a similarity-weighted success rate. A language model is used in exactly two optional places (drafting a playbook, refining a detection use case), both off until an administrator confirms a call, and neither output does anything by itself. Quanta never changes your systems: playbooks that act send a signed request to an endpoint you own, after a second person approves.

02Alert intake and the first look

The first look is the work a first-line analyst does on every alert, done the same way every time and written up for them to check. It never closes an alert; when a case opens from it (§04), the alert is marked investigating.

Intake

Alerts come in through POST /api/ingest/alerts (a key with the soc:write scope) or as OCSF Detection Finding events (class 2004) through /api/ingest/alerts/ocsf. An alert is unique by source and external id, so a re-send changes nothing. The OCSF mapping reads finding_info (uid, title, analytic name, attacks), severity_id (1 informational to 5 critical; 6 shown as Critical; unknown becomes Medium), the device, user and endpoint objects, and the reported action taken. It is a subset mapping written from the public schema, not a validator.

The verdict

Signals and weights live in remediation/config/soc_triage.yaml. Each signal that fires adds its weight to a likely-true-positive or likely-false-positive score, and the reasons returned name every signal.

SignalWeightPoints toward
An indicator flagged by enough reputation engines (endpoint alerts need 20, others 10)3True positive
An open known-exploited vulnerability on the host matches the alert's technique2True positive
An earlier true positive on the same host or from the same rule within 7 days2True positive
The SIEM shows matching events on the host1True positive
Critical severity1True positive
The rule's closed alerts are overwhelmingly false positives (90% of at least 10)3False positive
Every looked-up indicator is known and none flagged1False positive
The same rule on the same host was closed benign or false positive before2False positive

A score of 3 or more on a side gives that verdict; 5 or more is high confidence. Thin or mixed evidence gives escalate-l2, never a guess at closing. A Critical alert is never called a likely false positive automatically. Reputation lookups and SIEM searches happen only when an administrator confirms: the preview lists exactly which public indicators would be sent, and the searches are read-only.

Priority order in the queue

Alerts are ordered by severity base (Critical 100, High 70, Medium 40, Low 15, Informational 5) plus 30 for a known-exploited vulnerability on the host, 20 when a finding on the host carries the alert's technique, 10 for a high exploit-probability finding, and 10 when the host has no owner. The reasons are shown. This orders work; it does not change the alert's severity.

03The investigation report, step by step

A report is assembled, not written. Each section answers a question an analyst would otherwise answer by hand and says where its answer came from. A section with nothing to say says so, because an empty result is information.

  1. Verdict and why. The recommendation and every signal behind it (§02).
  2. Incident summary. What the alert is, on what host, how long ago, and what else Quanta knows about the host: open and known-exploited vulnerabilities and its owner.
  3. Historical correlation. For each host, user and address, how many earlier alerts involve it and how they were closed, plus what a SIEM history search found (when confirmed). The look-back is limited to 90 days by default (max_lookback_days), widened to 365 only with a written justification, and the report says when it was widened.
  4. Associated entities. The host and its owner, the user and whether they hold privileged access (from Access Governance), and the addresses, domains and hashes.
  5. ATT&CK mapping. The technique and tactic from the table in attack_tactics.yaml and what to check next for it.
  6. Attack flow. Alerts on the same host or user in time order, labelled by tactic, so the reader sees where this alert sits in a sequence.
  7. Indicators. Each public indicator with its reputation when looked up. Private and documentation addresses are never sent.
  8. Blast radius. Where else the same indicators appear in stored alerts and in the SIEM, and what is exposed on those hosts.
  9. What your tools did. The action the EDR or firewall reported (blocked, quarantined, allowed) and whether it needs checking. An "allowed" on a likely true positive is called out.
  10. Recommended actions. From the verdict, the signals, the matching runbook and the rule's history, with the playbooks that could carry each action.
  11. References and timeline. The searches that were run with counts, the detection rule, the runbook, and the events in order.
  12. Follow-ups. Questions asked after the first report, answered from the same data and merged in.

The report is available as Markdown and as a self-contained HTML page. Because nothing is generated by a model, the same alert and data always produce the same report.

04Cases, queues and escalation

ITIL-style incident handling applied to security alerts. The rules are in remediation/config/soc_ops.yaml, read on every request.

Tiers and queues

L1

Triage

First look at every case. Confirm or dismiss, gather the obvious evidence, escalate what needs depth. May resolve as false positive, benign, duplicate, insufficient data or true positive.

L2

Investigation

Deeper investigation, scoping, containment recommendation, hand-off to response. May also accept risk.

L3

Response and hunting

Major incidents, malware and forensic analysis, detection fixes, hunts that follow from the case.

An analyst belongs to one tier and cannot be assigned a case in a higher queue. Assignment suggestions go to the least-loaded analyst of the tier who is under max_open_per_analyst.

Priority: impact times urgency

Impact is single (one host or user), multiple (2 to 5) or widespread (6 or more), raised one step by a person or by a privileged account; weights 1, 2, 3. Urgency comes from the alert's severity: Informational and Low 1, Medium 2, High 3, Critical 4. The product gives the priority by the first threshold met.

PriorityScore at leastAcknowledgePick up after escalationResolve
P1915 min15 min4 h
P2630 min30 min8 h
P332 h2 h24 h
P408 h8 h72 h

The clocks are derived from timestamps on read, so nothing needs to be kept in sync. A clock is met, running, at risk (past 80% of target) or breached.

Escalation

  • Functional. An analyst escalates to a higher tier and must write a hand-off summary of at least 20 characters: what was found, what was done, what is left. The case moves to that queue, the owner is cleared, and the pickup clock starts. The summary becomes the case summary.
  • Hierarchical. When a case has been in its tier longer than its resolve target, the periodic sweep moves it up one tier, once per tier, and records an event saying why. A person is never silently overruled: an automatic escalation is an entry in the history like any other.
  • Resolve and close also need a written summary. Reopening needs a reason and counts toward the reopen rate. Resolving a case closes its alerts with a matching disposition.

Automatic cases

After an alert is investigated, a case opens in the L1 queue when the verdict is in the configured list (likely true positive or escalate-L2), the severity is Medium or above, the alert has no case yet, and fewer than 30 automatic cases opened in the last hour. The recommendation is stored on the case so its accuracy can be measured later (§05).

Case summary notes

Every case carries a summary. Until someone writes one, Quanta shows a deterministic summary built from the facts on the case: priority, queue, impact, techniques, hosts, account, linked alerts, the recommendation, owner, and escalation and reopen counts. The analyst's own note replaces it on escalate, resolve and close, and both remain visible.

06Log investigation

Paste log lines on a case and get structure and anomalies back. Everything is classical statistics on the text given; it runs inside Quanta and nothing is sent anywhere.

Each line is read as JSON, as key=value pairs or as plain text, with a leading timestamp when present; at most 20,000 lines are read.

FindingHow it is found
Top valuesMost common users, source and destination addresses and processes.
Rare valuesA value seen once in a field where other values repeat.
BurstsEvents per minute; a minute is a burst when its z-score ((count - mean) / standard deviation) exceeds 3 and it has at least 10 events.
BeaconingA source and destination pair with at least 6 events whose gaps are regular: coefficient of variation (standard deviation / mean) below 0.2 and a mean gap of at least 5 seconds.
Failures then successFive or more failed sign-ins for an account or address followed by a success, the usual shape of a guessed or sprayed password.
IndicatorsAddresses, domains, hashes and URLs through the same extractor alert intake uses.
TechniquesThe TTP classifier (§07) over the lines that look like attacker activity.
Read the results as leads

A regular interval can be a health check, a burst a deployment, a rare value merely rare. When run from a case, a one-line finding is added to the case history.

07TTP identification

From text (an alert, a log excerpt, an analyst's note), which ATT&CK techniques does it describe? A multinomial Naive Bayes classifier, trained by counting on every call, so the same inputs always give the same answer.

Training data

  1. The phrase list ttp_lexicon.yaml: short examples written for each technique. Add your own wording; it retrains on the next call.
  2. The hunt library: each technique's name and the strings in its detections (process names, command fragments, patterns).
  3. Optionally, labelled history: the text of alerts analysts closed as true positive, labelled with the technique the alert carried, so the model learns the wording of this environment.

How a prediction is made

  1. The text is lower-cased and split into tokens (keeping forms such as -enc and /c), a trailing .exe and common endings are dropped, filler words are ignored, and adjacent pairs are added as features.
  2. For each technique, add up log P(token | technique) with add-alpha smoothing (alpha 0.1), over the tokens the model knows. Unknown tokens are ignored. A token counts at most three times.
  3. Each token is scaled by specificity, ln(classes / classes containing the token) / ln(classes), so a word present in many techniques counts for little and one present in a single technique counts in full.
  4. A softmax turns the scores into probabilities. The answer lists the top techniques with their probability and the tokens that pushed hardest toward each (the log-likelihood ratio against the other techniques), so an analyst sees why.
  5. An ATT&CK id written in the text is reported as stated, not inferred.

An answer is confident when the top probability is at least 0.5 and at least two distinct known tokens support it; otherwise it is shown labelled weak. If no token is known the answer is no technique. On the nine test sentences shipped with the tests, the right technique ranks first for each, and unrelated text is not confident.

Limits, stated plainly

It recognises wording it has seen, not behaviour; an attacker who renames tools defeats it; the phrase list covers the techniques in attack_tactics.yaml and nothing else; and probabilities are relative to those techniques only. It is a prompt for an analyst, which is how the interface presents it.

08Threat intelligence

Turn a report into the facts a hunt needs, and say how much it matters to this environment. Extraction uses explicit patterns, no model.

Input is plain text (an advisory, a post, extracted PDF text) or a STIX 2.1 bundle. Extracted: CVE ids, ATT&CK technique ids, indicators (public addresses, domains, hashes, URLs) and threat-actor names. Relevance to this estate is a score out of 100 with reasons:

PointsWhen
+40A CVE in the report is open on an asset in the estate (+10 more if on CISA's KEV list)
+25A technique in the report is tagged on the estate's open findings
+15A technique in the report has hunt queries in the library
+10The report names an indicator type that can be swept (address, domain, hash)

60 or more is high priority, 30 or more medium, else low. A report matching nothing in your estate is low priority, not discarded. The proposed hunt takes its hosts from the assets carrying the report's CVEs, its queries from the library for the report's techniques, and adds one query that sweeps the indicators. Reports are de-duplicated by content hash.

09Hunting and hunt reports

A hunt starts from a hypothesis, runs read-only leads against your SIEM only after an administrator confirms, and ends with a recorded outcome, because "we looked and found nothing" is a result.

Where hunts come from

  • Exposure. A CVE on CISA's KEV list (or with a high EPSS score) that is open on at least one asset becomes one hypothesis: someone may already have exploited it on these assets. The techniques are those tagged on the findings; the queries come from the hunt library.
  • Threat intelligence. A relevant report (§08).
  • Manual. An analyst's own hypothesis.

Lead and hunt verdicts

Lead (one query)Meaning
not-runNot run or errored, so nothing to say
no-hitsRan and returned nothing
likely-fpReturned results the analyst judged benign
possible-tpReturned results that are suspicious, or not yet assessed. Unassessed hits are never assumed benign
confirmed-tpReturned results the analyst judged malicious

The hunt's overall verdict: confirmed-compromise if any lead is confirmed; multi-hit-correlated if two or more leads are possible, or the same host, user or address appears in the samples of two or more leads; low-confidence if exactly one lead is possible; no-findings if every lead that ran is no-hits or likely benign; incomplete if nothing has run.

How a hunt report is generated

  1. Each lead's recorded result, count, sample and assessment gives the lead verdict above.
  2. Entities in the samples (host, user, address fields) are compared across leads to find correlated entities.
  3. The overall verdict and an executive summary (what was hunted, how many leads ran, what was found, which entities recur, which enabled detection rules already cover the techniques) are computed.
  4. The report is rendered: verdict and headline, executive summary, hypothesis, scope (techniques, hosts), a trial-hit execution summary table (status, hits, affected entities), a section per detection domain, correlated entities, analyst notes and follow-ups.
  5. It is served as Markdown or as a self-contained HTML page. Nothing in it is written by a model.

Every lead is a read-only search with the look-back window recorded on it; the report headline states how many leads ran, against which sources and over which windows. Hosts, techniques and the enabled rules that already cover each technique are named, and techniques with no enabled rule are listed as candidates for a new detection (§11).

10SOAR and guided playbooks

A playbook is a short list of steps run against an alert. Quanta never acts on your systems itself.

The engine

  • Steps: investigate, enrich indicators, add a note, update an alert status (investigating or similar; never closing it), notify, request approval, response action, each optionally conditional on the investigation.
  • Response actions (create ticket, enrich asset, isolate host, block address or domain, disable account, revoke sessions, reset credentials, quarantine file) are sent as signed webhook requests (HMAC) to an endpoint you own. An action that changes something always needs a request-approval step ahead of it in the same playbook.
  • Second person. The person approving must differ from the person who started the run (require_second_person).
  • Dry run first. A dry run contacts nothing and changes nothing; destructive actions are never sent in one.
  • Limits. At most 25 steps; at most 20 automatic runs an hour; an automatic start looks only at data inside Quanta.

Which playbook? The recommender

A small, transparent statistical model, not a neural network. For an alert it looks back over past runs and weighs each by how much its alert resembled this one:

similarity = 0.35 × same technique + 0.30 × same detection rule + 0.20 × same alert category + 0.15 × same severity (each 0 or 1). Only past alerts with similarity of 0.3 or more count.

For each playbook the weighted number of such runs is W and the weighted number that completed is C. The rate is Laplace-smoothed, (C + 0.5) / (W + 1), and scaled by how much evidence there is, score = rate × (1 − 1 / (1 + W)), so a playbook used once on a near-identical alert does not outrank one used twenty times. Also shown: how often the alert was then closed, and whether the playbook needs a second person. With no usable history it falls back to playbooks whose own trigger matches the alert, and the basis (history, trigger or none) is always reported. A recommendation never runs anything.

AI-drafted playbooks (optional)

  1. An administrator asks for a draft and sees the prompt first. It holds only the alert's category, technique, rule and severity, the permitted step types and the permitted actions. Free text from the alert is never included, which closes the prompt-injection route.
  2. Only after confirmation is the model called, subject to the daily per-user token cap, and the usage is recorded.
  3. The reply is parsed and run through the same validator every playbook goes through. Unknown steps, disallowed actions, a destructive action without an approval before it, and too many steps are rejected with the validator's own message.
  4. What comes back is a draft to edit and save yourself. It is never saved or run by the drafting step.

11Detection engineering and use-case generation

How well each rule works, which techniques nothing detects, and what to build next, each with a hypothesis, its evidence, a draft rule and a test plan.

Rule health

Per rule, over the policy window: decided alerts = true positive + benign + false positive. Noise rate = (false positive + benign) / decided. Health tier, first match wins: Low Volume (too few decided to judge), High Fidelity, Low Value, Critical Noise, Noisy, Healthy, each with a recommendation to maintain, tune or disable. A tuning suggestion shows the rule's detection block before and after a filter excluding the hosts behind most of the noise, with the reduction estimated from the data. It is for an engineer to review and test; nothing is pushed to a SIEM.

Where new use cases come from

GeneratorPattern recognisedHypothesisDraft
Coverage gapA technique tagged on open findings, named in intelligence reports or hunted, that no enabled rule claimsAn adversary using it would go unnoticedThe library's detection as a Sigma rule
Hunt promotionA hunt lead assessed suspicious or malicious with hitsWhat a hunt found once should be detected continuouslyThe lead's detection as a Sigma rule
SequenceA pair of tactics following each other on the same host within a window (24 h) across at least 3 hosts, with at least 50% of those hosts closed true positiveThe pair together is more telling than either alert aloneA Sigma temporal-ordered correlation
Indicator watchlistThe public indicators of a relevant intelligence reportContact with them is worth an alert while the report is currentA Sigma rule over the indicator lists, with a 90-day review note

The score (0 to 100) adds to a base for known-exploited findings, intelligence mentions, hunts and estate size, or, for sequences, for precision and support. The mining is counting, not machine learning: a pattern is proposed when enough distinct hosts show it and enough of them turned out to be real, and the evidence is shown so an engineer can judge it. Thresholds are in detection_policy.yaml.

Lifecycle

Proposed, then accepted (an engineer will build it), implemented (it is live), rejected or deferred. Every decision needs a note. A draft is never counted as coverage; coverage counts only enabled rules in the inventory. Optionally a model can add a sharper hypothesis, evasion ideas, false-positive sources and test ideas beside a use case, from counts and ids only, stored as a labelled suggestion that does not change the draft rule.

13Limits and honest status

  • The SIEM search, reputation, response and notification connections are built against public documentation and tested against hand-written fakes; none has been run against a live tenant.
  • The OCSF mapping is a subset written from the public schema and has not been run against a live producer.
  • The classifier and statistics recognise wording and patterns, not behaviour; they prompt an analyst and never replace one.
  • Recommendation accuracy and precision figures are only as good as the dispositions analysts record.
  • Sigma drafts are starting points: field names must be matched to your data model and the rule tested on real data before it is switched on.
  • The two optional model calls need the Claude Code command-line tool and spend API usage, which the daily cap bounds.
  • Quanta records and measures the work and drafts artifacts. It does not change your firewalls, accounts, hosts or SIEM.
