RBAC, Multi-Tenancy & Governance

Exactly what today's access model enforces, exactly what the MSSP tenant view is and isn't, and every policy an admin can shape without touching code.

01The real role model

Deliberately simple, not an idealized granular permission matrix: one boolean role, plus one independent scoping field.

AxisValuesWhat it controls
Roleadmin | (not admin)Every mutation route requires a logged-in session at minimum; most require role == "admin" outright (policy edits, user management, connector fetch/scan actions, approvals).
Teama string, or noneNarrows which findings and approvals a non-admin's own queries return — enforced server-side, per request, not a client-side filter.

A third kind of principal sits beside people: the API key, a scoped machine credential for tools that call Quanta (see the Connectors & Adaptors Catalog, §08). Keys carry only the scopes ingest:write, tickets:update, read:findings, controls:write (push controls), ai-usage:write (push AI usage events), soc:write (push alerts, threat intelligence and ITSM tickets to the SOC), darkweb:write, api:write, asm:write (import attack-surface tool output) and mcp:read (the read-only MCP endpoint); a key can be bound to one team and then sees only that team's findings and assets; Quanta stores a hash only (qk_… keys are shown once), each key has an expiry, can be revoked at any time, is rate limited per key (QUANTA_API_KEY_RATE_MAX, default 600 a minute) and appears in the activity log as apikey:<name>. A key grants no admin role and no access to any other route.

The one gap worth knowing before a real rollout

Every read (GET) route is public by default in this MVP — team-scoping included, meaning it's bypassable by an anonymous request unless QUANTA_REQUIRE_LOGIN_FOR_READS=true is explicitly set. This is a disclosed, deliberate MVP default, not an oversight — but it means "team scoping" today protects against an authenticated user browsing outside their lane, not against an anonymous one.

The login gate has a narrow, deliberate exemption

With QUANTA_REQUIRE_LOGIN_FOR_READS (or QUANTA_PRODUCTION) on, only /api/ingest/, /api/inbound/ and /api/export/ skip the browser-login check, because tools cannot sign in through a browser. Each of those routes verifies an API key itself and rejects a missing, expired, revoked or out-of-scope key. In production the older POST /api/ingest/generic webhook requires an ingest:write key as well.

One inbound endpoint uses a shared secret, not a key

POST /api/inbound/git-webhook receives GitHub or GitLab pull request events and carries no login or API key. Each delivery is verified against QUANTA_GIT_WEBHOOK_SECRET (GitHub's HMAC-SHA256 X-Hub-Signature-256 over the body, or GitLab's X-Gitlab-Token). With no secret configured it refuses every delivery (503), a bad signature gets 401, and a pull request Quanta did not open is ignored. It can only update the recorded open, merged or closed state of a pull request Quanta opened; it cannot write to a repository. Tested against hand-signed payloads, not live deliveries.

02The MSSP tenant view — what it is, and isn't, today

A tenant switcher exists in the UI ("All Tenants (MSSP view)" plus named demo tenants). It is important to be precise about what this actually does:

What it is

A client-side filter over one shared dataset — selecting a tenant narrows the same findings by asset type, illustrating what a per-client slice of the dashboard could look like.

What it is not

Real per-tenant authentication, a real per-tenant data boundary, or server-side tenant isolation of any kind. Every tenant sees data drawn from the same underlying store.

Held to a named standard, not waved away

An internal security review of this exact gap concluded there is zero server-side tenant trust today, and named the standards a real implementation must satisfy before this becomes a genuine multi-tenant claim: NIST SP 800-53 AC-3/AC-4/AC-6 (access enforcement, information flow, least privilege), OWASP API Security Top 10:2023 API1 (Broken Object Level Authorization), OWASP Top 10:2025 A01 (Broken Access Control), and OWASP ASVS 5.0 V8 §8.3.1. Real multi-tenancy needs a genuine per-tenant data boundary layered onto the database and auth foundation that already exist today — not something to bolt onto the current shared-dataset model incrementally.

03Audit trail

The Activity Log (/activity-log) records who did what, when — every approval decision, exception grant, policy edit, and connector fetch/scan action — with a lightweight statistical anomaly flag (an actor or action volume that deviates from the recent baseline) surfaced separately from the raw feed.

05Standards & compliance mapping

Read this before using any mapping below for anything

This is an informational reference only. It maps existing technical capabilities to common compliance-framework control categories, for internal planning — it is not a certification, attestation, audit result, or compliance claim of any kind, for any framework.

Achieving actual SOC 2, NIST CSF, PCI DSS, or any other formal compliance status requires a licensed audit or formal third-party assessment. Do not present this mapping, or any summary of it, to a customer, auditor, or regulator as evidence of compliance.

Frameworks referenced elsewhere in this product, strictly as directional category mappings: NIST Cybersecurity Framework (CSF), NIST SP 800-40r4 (patch management), CIS Controls v8 (§7.1–7.6), ISO/IEC 27002:2022 (§8.8, §8.32), and NIST FIPS 203/204/205 (post-quantum cryptography). Named gaps, stated rather than omitted: automated scheduled vulnerability scanning (CIS §7.5/7.6 — Quanta ingests already-scanned findings; OpenVAS/GVM is the one exception that scans directly), automated patch deployment (§7.3 — deliberately never executed), and vendor-advisory/config-drift monitoring (not covered).

06AI & security guardrails

Mapped against the current OWASP Top 10 for LLM Applications (2026 edition, published August 2026) — the standard this class of risk is actually tracked against, not an ad-hoc checklist. Real fixes below, and one real gap disclosed rather than papered over.

It writes only to a new branch, never the default or a protected branch, and never merges. Denied paths cannot be touched by any proposal (pipeline definitions under .github/**, CODEOWNERS, key files, environment files), and a code fix is limited to the finding's own file. Disclosed gap, not fixed here

The daily AI token limit (Admin Settings) is real and enforced pre-flight, but defaults to unlimited until an admin sets one - not a bug, an opt-in cap rather than a surprise restriction on an unconfigured deployment.

07Access to GRC, hunting & related pages

The newer governance and security-operations pages follow the same two-role model: they are admin-only, with two narrow exceptions that need only a login. Like every other read, the data behind them is open to anonymous GET requests only where the deployment leaves reads public; with QUANTA_REQUIRE_LOGIN_FOR_READS or QUANTA_PRODUCTION on, the routes are gated as described here.

PageWho can use itRule worth knowing
/grcAdmin. Policy list and policy acknowledgement need login only.Accepting a risk requires the reason (in the treatment plan) and a review date. Automated control tests with too little data return na, never a pass. Attestations sit beside the evidence and do not replace it.
/threat-modelsAdminAccepting a threat or marking it not applicable requires a note saying why.
/api/licenseLoginReports which of the eight modules the installed licence covers. In enforce mode a route of an unlicensed module answers 403; core routes (sign-in, the findings store, support, connections, administration) never do. See docs/LICENSING.md.
/api-securityAdminSending a policy is confirm-gated; a blocking policy needs approval of that exact version by a different administrator, and any edit voids it. Machine routes (/api/ingest/api-traffic, /api/ingest/openapi, /api/ingest/api-test-results, /api/inbound/api-policy-status) need an api:write key. Quanta never changes a WAF itself; the policy goes as a signed request to a URL the customer owns.
/huntingAdminClosing a hunt requires an outcome (confirmed, not-found or needs-data). Closing an alert requires a disposition (true-positive, benign, false-positive or needs-data).
/ai-usageAdminReads usage counts and cost figures only; no prompt text is ever stored.
/controlsListing needs login; add, delete and import are adminThe inventory feeds compensating-control assessments. Automated pushes use a controls:write key.

/pipeline-gatesLogin to view and try an evaluationCI calls GET /api/gate/evaluate with a read:findings key; every evaluation is recorded.

Machine intake for these areas uses API keys, not sessions: soc:write for POST /api/ingest/alerts, ai-usage:write for AI usage events and OTLP traces, controls:write for controls, asm:write for attack-surface imports. A key with one scope cannot call a route that needs another. The MCP endpoint (POST /mcp) sits outside /api/, accepts only a key with mcp:read (never a browser session, never a token in a URL), re-checks the scope on every tool call, and is off unless QUANTA_MCP_ENABLED=true. The incident, routing, investigation-report, hunt-suggestion, integrity and attack-surface routes need an administrator session; the typed-decision evaluate and policy routes need a login, and calibration needs an administrator. A decision may be routed to auto only when its policy says reversible and local and the code says it does not touch an environment; that flag is not in any editable file.

Evidence, not certification

The GRC module collects evidence, records decisions and tracks workflow against framework catalogs (built-in subsets of NIST 800-53 r5, CSF 2.0 and an AI-governance set, or a full catalog imported as OSCAL JSON). Its per-control status and OSCAL assessment-results export are inputs to an assessment. They are not a certification, attestation or audit result, and the same caveat as in §05 applies. Quanta is also not a SIEM: hunts propose queries that an analyst runs in their own tool and records the result of.
