Reporting & Scheduled Delivery

What a VulnHunter report actually contains, how to generate one on demand, what's real about scheduled email delivery — and what genuinely isn't yet. Every claim on this page is traced to dashboard/reports.py, remediation/notifications/report_scheduler.py, and the live /reports page, not an aspirational feature list.

The short version

Report content is always a real, live-computed snapshot of this repo's current findings — there's no sample data and no historical trend line yet, because there's no historical/time-series storage to trend from (a real local SQLite database now backs several other record stores — see the Architecture doc's storage-model section — but report snapshots aren't one of them yet). Report delivery is a separate concern, and here the honest answer surprises people both ways: on-demand generation is real (§02), and recurring email delivery on a schedule is also real, working code today (§04) — not a roadmap idea. What's genuinely still roadmap is narrower than "scheduling": real historical aggregation, custom field selection, and calendar-aware timing. §05 draws that line precisely.

01What a report contains today

Every report — whether generated on demand from /reports or emailed on a schedule (§04) — is assembled by one real function, generate_report_data() in dashboard/reports.py, over the exact same live data every other dashboard page reads: the re-scored remediation queue, the static REMEDIATION_PLAN.md snapshot, code-scan results, and generated playbooks. Nothing is sample text.

FieldWhat it actually measures
sla.breached / at_risk / on_trackReal counts from the live queue's own SLA due-dates. "At risk" means due within 3 days and not yet breached; everything else on track.
kev_countIn-scope findings CISA's Known Exploited Vulnerabilities catalog confirms as actively exploited right now.
high_epss_countIn-scope findings with a live FIRST.org EPSS exploitation-probability score ≥ 50%.
remediation_totalCount of infrastructure/application findings in scope (the live queue, filtered).
vulnhunt_totalCode-scan (SAST) total from SECURITY_REPORT.md — landscape-wide only; reads as 0 the moment a scope or team filter is applied (see the callout below).
playbook_countReal generated Ansible playbooks sitting in remediation/output/ — landscape-wide only.
risk_tier_countsThe static REMEDIATION_PLAN.md snapshot's auto-approvable / needs-change-approval / manual-only breakdown — landscape-wide only.
asset_type_breakdownIn-scope findings grouped by asset type (OS, network, IoT, application, certificate, …), sorted by count descending.
top_priority_findingsThe 5 highest-priority in-scope findings — ID, title, priority tier, and asset.
period / scope / teamWhat you asked for: a cadence label (§05), one of 9 sub-domains or "all," and an optional team filter.
Scoping a report excludes two things, on purpose

Pass a scope (e.g. dast) or team filter and the report honestly says so via a scope_note: code-scan/SAST findings have no scan-type or team association in that data path, and REMEDIATION_PLAN.md's risk-tier snapshot and playbook count are whole-pipeline artifacts that can't be filtered this way. Both zero out rather than silently mislead — a scoped report is real, just narrower.

One field is computed but not yet surfaced anywhere: vulnhunt_auto_fixable is present in the raw JSON response but isn't rendered in either the downloadable HTML report or the on-screen summary today — a real, minor gap between what's computed and what's displayed.

02Generating a report on demand

Any logged-in user can do this — generating a report doesn't require admin (see §07).

How do I generate a report right now?/reports
  1. Open Reports from the sidebar.
  2. Choose a Period from the one dropdown on the page — Daily, Weekly, Monthly, Quarterly, Half-Yearly, or Yearly — and click Generate.
  3. The page renders 8 KPI figures (SLA breached/at-risk/on-track, CISA KEV-listed, High EPSS, Infra findings, Code vulnerabilities, Playbooks generated) and a Top Priority Findings table. Every KPI is a live link that jumps straight into a pre-filtered Queue, Code Scan, or Remediation Plan view — this isn't a static screenshot, it's a doorway into the live data behind it.
  4. Click Download this report as HTML to get the identical report as a standalone file — inline CSS only, no dependency on the dashboard's own stylesheet, so it opens correctly anywhere.
Two parameters the API supports that the page's form doesn't expose yet

Both /api/reports/generate (JSON) and /api/reports/generate.html (HTML, add &download=true for an attachment) also accept scope= (one of 9 sub-domains: all, infra-vm, sca, cert-mgmt, dast, iac, secrets, runtime, ai-ml) and team= query parameters. They're real and reachable by URL today — they're exactly what powers scheduled subscriptions in §04 — but the visible /reports page currently renders only the Period dropdown, not scope/team controls. See §05.

04Scheduled email delivery — real, not roadmap

This is worth stating precisely, because "does it schedule reports?" is easy to answer wrong in either direction: recurring email delivery of a report is real, working, wired-up code today, built from remediation/config/report_schedule_rules.yaml, remediation/notifications/report_scheduler.py, and remediation/notifications/email_sender.py. It ships with nothing configured by default, and it depends on real SMTP settings to actually send — but the mechanism itself is not aspirational.

How do I set up a scheduled report?/reports

The same /reports page has a "Schedule automatic email reports" panel below the on-demand generator: a raw YAML text box, not a dropdown form. Each subscription entry sets:

  • id — a unique string, used to track when it last sent
  • scope — one of the 9 sub-domains from §02, or all
  • team — a team name exactly as it appears in the asset-ownership store (the shipped example uses "Identity & Domain Services")
  • cadence — weekly, monthly, quarterly, half-yearly, or yearly (no daily option — see below)
  • recipients — a list of email addresses
  • enabled — true/false; disabled entries stay editable but never send

Saving requires an admin session (POST /api/report-schedule). The file ships with subscriptions: [] — real mechanism, nothing scheduled out of the box until an admin adds one.

How a due subscription actually gets sent

1. Something checks if it's due

An in-process timer inside the dashboard server runs the check hourly by default (NOTIFICATION_CHECK_INTERVAL_SECONDS). Due = enabled, and at least cadence's day-count has elapsed since it last sent — a rolling window, not calendar-aware.

2. The real report is built

The exact same generate_report_data() from §01, scoped to that subscription's scope/team. No separate "scheduled" data path.

3. Real SMTP sends it, if configured

email_sender.py — stdlib smtplib, STARTTLS by default. Until SMTP_HOST/SMTP_PORT/SMTP_FROM_ADDRESS are set as real environment variables, a due send is honestly reported as skipped, never faked as sent.

4. No double-sends

The last-sent timestamp lives in its own schedule_state.json, deliberately separate from the YAML file, so a server restart can't resend the same period and an admin's own comments in the rules file are never overwritten.

For delivery that doesn't depend on the dashboard process staying up around the clock, the identical check is exposed as POST /api/notification-settings/run-checks-now (admin-only) — point a real external cron or Windows Task Scheduler at it instead of relying on the in-process timer.

Honest limits on scheduling — real gaps, precisely stated

Cadence is a rolling day-count (7/30/91/182/365 days), not calendar-aware — there's no "every 1st of the month" primitive yet. There's no daily schedule cadence (daily exists only as an on-demand period label in §02). A scheduled send still reflects the same live current-moment snapshot as an on-demand report — a monthly email really goes out monthly, but its content is what's true right now, not an aggregated summary of that month (see §05). And like every other connector in this repo, the SMTP sender is built against the standard protocol but hasn't been exercised against a real mail server yet — send a real test via Notification Settings (§06) before relying on it.

05Customization: today vs. roadmap

This is the distinction that matters most on this page. The line below is drawn from what's actually wired up in code, not from what would make a better feature list.

Today — real and working

• Period label on the on-demand generator (6 options)
• scope + team filters via URL/API params (9 scopes) — powers scheduling, not yet a dropdown on the on-demand form
• Standalone self-contained HTML download, plus raw JSON at the same endpoint (unlinked from the UI)
• Real recurring email delivery per sub-domain/team/cadence, YAML-configured, admin-managed
• Real SMTP sending once configured, with a preview-before-send step and an explicit confirm+admin gate on any actual send
• On-screen KPI figures that deep-link into pre-filtered Queue/Code Scan/Remediation Plan views

Roadmap — not yet, named honestly

• Real historical trending / period-over-period aggregation (needs a findings-history datastore)
• scope/team as dropdown controls on the on-demand form itself
• Custom field/metric selection — the report's shape is fixed in code
• Saved/named report templates beyond the scheduled-subscription list
• Export formats beyond HTML/JSON (no PDF, no CSV/XLSX for this snapshot)
• Calendar-aware scheduling, and a daily schedule cadence
• Delivery durability independent of server uptime without an external cron

Why "period" isn't the same claim as "scheduling"

These are two separate, easily-conflated facts. Report content has no history: the Period selector (daily…yearly) labels intended cadence, but every period — on demand or scheduled — renders the same real, current-moment snapshot, because there's no historical trend/time-series storage to aggregate report periods from yet — real persistence exists now for other record stores, just not this one (see dashboard/reports.py's own module docstring, and KNOWLEDGE_TRANSFER.md's roadmap). Report delivery is a different question, answered in §04: recurring email delivery on a schedule is real, shipped code today, just not yet populated with any subscription by default and dependent on real SMTP configuration to actually send.

06Notification Settings — the fuller picture

/notification-settings is where the report-scheduling story connects to a second, complementary mechanism.

Same schedule editor

The identical report-schedule YAML from §04, editable here too.

Team alert subscriptions

A distinct, complementary rule set (alert_rules.yaml) for critical findings, zero-days, and KEV/EPSS matches — not a periodic report, an event-triggered alert.

Preview → confirm → send

Build the exact real subject/text/HTML body first, free. Actually sending a test needs a real recipient, an explicit confirm, and an admin session.

A "Run checks now" button here calls the same POST /api/notification-settings/run-checks-now endpoint described in §04 — useful for verifying a new subscription without waiting for the next hourly tick. A status readout shows whether SMTP is actually configured on this server, honestly, before you rely on either mechanism.

07Navigating reports — RBAC & the Overview companion

Access here follows this product's deliberately simple RBAC model — one boolean role plus one independent team-scoping field, enforced server-side (see the RBAC, Multi-Tenancy & Governance document for the full model). For reports specifically:

ActionWho
View/generate an on-demand reportAny logged-in user — the read route carries no role check
Edit the scheduled-delivery YAML (§04)Admin only (POST /api/report-schedule)
Trigger "Run checks now" / send a real test emailAdmin only
One precise difference from Queue, Assets, Exceptions, and Approvals

Those four pages get real, automatic, server-side filtering to a logged-in non-admin's own assigned team. Reports do not work that way: a report's team filter (§01/§02) is a parameter someone explicitly supplies, not something inferred from the caller's session. Logging in with a team assigned doesn't, by itself, narrow what a report shows.

Reports vs. Overview — two honest answers to "what's our posture right now?"

The Overview page (/) is the always-on companion to the on-demand/scheduled snapshots on this page: the same KPI family (SLA, KEV, EPSS, coverage), refreshed automatically every 20 seconds, with the real charts described in §03 sitting alongside them. Reports exists for the moment you need that same real data as a static, shareable, emailable artifact — a point-in-time export, not a live view. Use Overview to watch; use Reports to hand someone a snapshot.

Putting it together, end to end
  1. Log in — any role can proceed.
  2. For continuous monitoring, leave Overview open; it refreshes itself.
  3. For a snapshot to share outside the dashboard, go to Reports, pick a period, generate, and download the HTML.
  4. If a team or leadership group needs this recurring: an admin adds a subscription in the "Schedule automatic email reports" panel (§04), and confirms SMTP is configured via Notification Settings (§06) with a real test send first.
  5. For event-driven signals instead of a periodic snapshot (a new critical finding, a zero-day, a KEV match) — that's the separate team-alerts mechanism, also on Notification Settings.
