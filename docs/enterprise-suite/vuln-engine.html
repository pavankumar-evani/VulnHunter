Vulnerability Finding Engine

How a real vulnerability gets from a scanner, cloud posture tool, or asset directory into a scored, threat-intel-aware finding — and the one engine in this catalog that can generate findings from nothing, not just relay them.

01Source taxonomy

Every integration in VulnHunter falls into exactly one of three categories. The category decides how much judgment is required to turn its output into a finding — which is why some sources write straight into the dashboard and others need one extra, human-supervised step.

ACVE-scoped host vulnerability

Tenable · Qualys · OpenVAS/GVM. Reports a CVE against a specific host. Needs judgment to classify the host into one of 17 asset types before it can route to a fixer — so these write a raw export file, not a finished finding, pending one agent-driven ingestion step.

BAlready-normalized posture

Prisma Cloud · Cortex XSIAM. Cloud posture violations and correlated detections arrive already asset-typed (cloud-infrastructure, unknown) — deterministic, direct-to-schema, no classification judgment needed.

CAsset inventory (no findings)

Infoblox · Axonius · Active Directory. These don't report vulnerabilities at all — they establish real ip/mac/hostname ground truth, reconciled into the asset registry so findings from category A/B can be correctly attributed.

Why this taxonomy, not a flatter one

Collapsing categories A and B would either force every posture finding through an unnecessary manual step, or let host-vulnerability findings skip a classification judgment they genuinely need. The split is a direct consequence of what each source's own data actually carries — not an arbitrary design preference.

02The connector pattern

Every pull-style connector — 8 of them today — follows one contract, so a new one is a known shape, not a bespoke integration:

  • test_connection() — the cheapest real authenticated call the vendor's API offers, wired to a dashboard "Test Connection" button with no confirmation gate.
  • A fetch/scan action — gated behind an explicit confirm checkbox, since it's a real, potentially slow call against a real production system.
  • Credentials are per-request, never stored server-side — every connector page asks for them fresh.
  • A disclosed verification status: built against the vendor's public API documentation, unit-tested against mocked HTTP/LDAP/GMP responses shaped like that documentation — and honestly labeled when it has (KEV/EPSS) or hasn't yet (every vendor connector) been exercised against a real live account.

03OpenVAS / Greenbone (GVM) — the scan engine

Every other integration above pulls data out of a scanner someone already bought and pointed at their network. This is the one that is the scanner — the answer to a customer with no existing vulnerability-management tooling at all.

Why a 4-step flow, not one "Fetch" button

Every pull connector above has one blocking action because the source already ran its scan. GVM is different — VulnHunter has to launch the scan itself, and a real authenticated network scan can run for minutes to hours. Blocking one HTTP request that long is the wrong shape, so the flow is Test Connection → Start Scan → Check Status (poll) → Import Results, each a separate, fast call.

sequenceDiagram
    participant U as Admin
    participant V as VulnHunter
    participant G as GVM (GMP protocol)
    U->>V: Start Scan (target + authorization checkbox)
    V->>G: create_target, create_task, start_task
    G-->>V: task_id (returns immediately)
    loop until Done
        U->>V: Check Status
        V->>G: get_task(task_id)
        G-->>V: status, progress %
    end
    U->>V: Import Results
    V->>G: get_results(task_id)
    G-->>V: real per-host CVE results
    V->>V: flatten into Tenable's CSV shape
Authorization is enforced in the UI, not assumed

Starting a scan requires checking "I own or am explicitly authorized to scan the target(s) above" — scanning is a real, potentially disruptive action against real infrastructure, never a background/silent operation.

04Threat-intel enrichment

Every CVE-bearing finding is checked against two free, public, no-auth feeds — the only two integrations in this entire product confirmed working against a real live endpoint end-to-end, not just built against documentation.

CISA KEV

Known Exploited Vulnerabilities catalog — flags a CVE confirmed actively exploited in the wild, plus date added and known-ransomware-campaign-use.

FIRST.org EPSS

A 0–1 exploitation-probability score per CVE, refreshed daily by FIRST.org — catches high-risk CVEs KEV hasn't confirmed yet.

Live-verified, not just documented

Both feeds were built and tested against the real endpoints during development — the one place in this product where "live-verified" means exactly that, not "built against public docs."

A separate enrichment pass adds poc_available and user_interaction_required from two real NVD API 2.0 fields already present in the cached CVE data — never fabricated when the underlying field is absent.

Why this beats CVSS alone: a real example, not a hypothetical

CVSS is theoretical severity — the same score whether or not anyone is actually exploiting a CVE today. Two findings in this product's own sample data show exactly why that's not enough by itself:

FindingCISA KEVEPSS (30-day exploitation probability)Effect on priority
OpenSSL denial-of-service CVENot listed70.6%EPSS override forces at least a minimum elevated priority, despite no KEV confirmation
OpenSSH regression CVENot listed99.5%Same override, more forcefully — very likely to be exploited soon even though CISA hasn't (yet) confirmed active exploitation

Neither CVE is KEV-listed — a CVSS-only or a KEV-only view would under-prioritize both. EPSS is what catches them. This is what "threat-intel-aware prioritization" means in practice for a customer: a real external signal changing what a team works on today, not a slogan.

What KEV/EPSS change, and what they never touch

KEV/EPSS affect priority (how urgently to act) only — never risk_tier (how safe a fix is to auto-apply). An actively-exploited CVE on a domain controller is still needs-change-approval, just moved to the top of that queue. The full priority formula these overrides sit on top of is in the Scoring Layer section (§05) below.

From a CVE to a named threat actor: how the correlation chain works

KEV/EPSS answer "is this CVE dangerous." A separate correlation layer answers a different question: "which known attackers use techniques like this one, and do any of them target my industry?" Three real pieces chain together — each honestly scoped about its own limits:

1 · ATT&CK technique tagging

A keyword heuristic against each finding's title/description (e.g. "sql injection" → T1190). Not authoritative attribution — a rough tactical grouping, not a substitute for real technique analysis.

2 · Threat-actor group reference

6 real, MITRE-documented groups (APT28, APT29, Lazarus Group, FIN7, Sandworm Team, APT41), each independently verified against attack.mitre.org, tagged with the real industries MITRE's own pages document them targeting.

3 · Correlation against your data

Matches a group's known technique IDs against techniques already tagged on your current findings. The Threat Intel dashboard page surfaces which groups share real technique overlap with what's actually in your queue today.

4 · Attack-chain grouping

Findings sharing an asset get bucketed by their tagged tactic into entry/pivot/impact (remediation/enrichment/attack_chains.py) — fixing a pivot finding breaks every chain it sits in, even if the entry and impact findings both stay open. Same heuristic, not-runtime-validated caveat as tagging itself; no new CWE/CAPEC dataset, built entirely on the tagging above. See the /attack-paths page.

Read this before citing any group name in a report

A technique match is an illustrative cross-reference, not an attribution claim — the same honesty pattern as the ATT&CK tagging it builds on (a keyword heuristic, not authoritative attribution). Many groups share common techniques (phishing, PowerShell, valid-account abuse); a shared technique ID doesn't mean a specific finding was caused by, or is evidence of, that named group. Re-verify against attack.mitre.org before using this in anything formal.

Industry-specific correlation: real today, narrower than it may sound

The Threat Intel page filters that 6-group reference table by industry — a 12-sector taxonomy spanning financial services, healthcare, government/defense, energy, retail, and more. Each group's target-industry tags are drawn directly from sector names stated on that group's own MITRE page, not inferred or estimated. A per-tenant industry field on the (demo) tenant switcher is intended to eventually drive this automatically.

Honest scope — read before assuming more than this does

This is a 6-group reference list cross-checked against your findings' tagged techniques — not a live, subscribed industry-threat-intelligence feed. A group missing a given industry tag genuinely has no sector-specific victimology documented for it on MITRE's page today, not a gap in this product's coverage. Both shipped demo tenants are currently tagged the same industry, so the tenant-driven half of this doesn't yet demonstrate real industry-to-industry contrast — disclosed directly in the feature's own code comments. The manual industry filter works fully regardless of which tenant is selected.

Extending this into scoring — e.g. nudging a finding's priority when a group already known to target its asset's industry has a matching technique — is a natural next step the underlying data already supports. It is not implemented today, and this document isn't claiming otherwise.

06CVE / CVSS handling

Severity is read from CVSS v4.0 first, falling back to v3.1 then v3.0 only for CVEs the NVD hasn't yet rescored under v4.0 — applied consistently everywhere a CVSS-derived field is computed (severity band, PoC/user-interaction enrichment). The qualitative bands themselves (Critical/High/Medium/Low) are numerically unchanged between CVSS versions; what changed in v4.0 is the User Interaction metric gaining a third value (NONE / PASSIVE / ACTIVE) versus v3.x's binary NONE/REQUIRED.

09Compensating-control coverage, network reachability & SBOM-aware remediation

Three real, additive capabilities layered on top of everything above — each ships with an honest empty state until the underlying dataset exists, and none changes a score or a plan for an asset it has no data for.

Real coverage, not a suggestion

remediation/enrichment/control_coverage.py correlates a finding against a hand-maintained firewall-rule + EDR-policy dataset (remediation/config/security_controls.yaml, ships empty) to compute a real existing-coverage %, concrete recommended controls, incremental-coverage %, and residual-risk % — a documented, deterministic formula, not a black box. Shown on every finding's detail view.

True external exposure

remediation/enrichment/network_reachability.py walks a hand-maintained hop-by-hop path to the internet (remediation/config/network_topology.yaml, ships empty) and returns an allowed/denied/unknown verdict — answering "is this asset actually reachable," not just "does one rule say allow."

SBOM-derived blast radius

remediation/enrichment/sbom.py parses a real CycloneDX SBOM (remediation/sample-data/sbom.json) to show which other components depend on a vulnerable package — the /dependencies page, and (for an asset with at least one finding carrying a resolved dependency.package) a third Impact-score component alongside severity and asset criticality, same additive-only rule as coverage above. remediation-fixer-application (see the Remediation Engine document) generates the upgrade plan from the same data.

Manually-curated datasets, not live connectors

Neither security_controls.yaml nor network_topology.yaml is populated by a firewall/EDR-vendor API call — there is no such connector in this repo today. Same disclosed, honest posture as remediation/sample-data/threat_intel.json: real, usable data structures, hand-maintained until (or unless) a live connector is built for them.
