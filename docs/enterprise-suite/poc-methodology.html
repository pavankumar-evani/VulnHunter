Proof-of-Concept Methodology

A structured way to evaluate VulnHunter against your own environment — scoped, time-boxed, and measured against criteria you set before it starts, not after.

This is a template, not a case study

VulnHunter has not yet run a completed customer POC. Everything below is a recommended structure and a set of illustrative success metrics to adapt — not a report of a past engagement, and not a promise of specific results in your environment.

02The five phases

1

Scoping

Pick 1–2 real data sources to connect (an existing Tenable/Qualys account, or standing up OpenVAS/GVM if there's none), the asset scope (a subnet, a business unit), and who signs off on success.

2

Environment setup

Connect the chosen source(s) via Test Connection, run a first fetch/scan, confirm findings land correctly. No production changes happen in this phase — it's read-only against the source.

3

Success criteria sign-off

Agree the specific, measurable bar (see §3) before the run phase starts — the single most important discipline in a POC that's supposed to produce a real decision, not a vibe.

4

Run

The pipeline operates against real (or a representative subset of) findings: enrichment, scoring, planning, playbook generation, and — if in scope — a real approval-workflow trial with your own team.

5

Evaluation & decision

Score against the agreed criteria, review the honest gaps list (Vulnerability Finding Engine + RBAC/Governance documents) against your actual requirements, decide go/no-go.

03Success-criteria template

Illustrative starting metrics — replace with your own thresholds before sign-off:

MetricWhat it measures
Time to first findingMinutes from a connector's first successful fetch/scan to a finding visible in the queue
Threat-intel enrichment coverage% of CVE-bearing findings tagged with a real KEV/EPSS result
Time to first playbookFrom ingestion to a real, reviewable Ansible artifact for an eligible finding
Classification accuracy% of findings whose auto-assigned asset type your team agrees with on spot-check
Connector fitDo your actual sources match the live catalog, or does closing the gap need the reference-tier build-out?

04Roles needed

Your side

A technical owner with read access to the source system(s) being connected, and a decision-maker who can sign off on success criteria and the final go/no-go.

VulnHunter side

Someone who can stand up the dashboard, configure connectors, and — if OpenVAS/GVM is in scope — administer that stack (see the Vulnerability Finding Engine document §5 for its deployment footprint).

05What a POC will not do

Same execution boundary as production

A POC never applies a generated playbook to real infrastructure — that boundary doesn't relax for evaluation purposes. If validating an actual remediation end-to-end matters to the decision, scope a controlled, non-production target and run it through your own change-management process, same as a real deployment would.
