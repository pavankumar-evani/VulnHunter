Architecture & Schema Reference

How VulnHunter is actually built: the request path, the storage model, the one schema every data source normalizes into, and the security boundary that keeps it safe to run.

Every diagram and field below reflects the real, current codebase — not a target-state design. Where something is a known limitation rather than a finished feature, §8 says so plainly.

01System overview

VulnHunter is a single deployable web application: a FastAPI backend serving both a JSON API and a hand-rolled vanilla-JS single-page app, backed by a real local SQLite database for its record stores and flat files for pipeline output/policy, with an optional layer of Claude Code subagents doing the judgment-heavy work (classification, playbook drafting) that a deterministic script can't.

No separate services to stand up

One Python process (uvicorn) serves the API, the SPA shell, and every static asset. There is no message queue, cache layer, or microservice boundary to operate.

Two different "engines," one process

The deterministic engine (connectors, enrichment math, scoring formulas) runs as plain Python inside the request. The judgment engine (classification, playbook drafting) runs as a subprocess call out to Claude Code — see §5.

02Request lifecycle & middleware

Every HTTP request passes through three FastAPI middlewares, in this order, before reaching a route handler:

OrderMiddlewareWhat it doesDefault state
1Static no-cacheForces /static/* responses to revalidate (Cache-Control: no-cache) instead of trusting the browser's heuristic freshness — an edited JS/CSS file is never served stale.always on
2Secure headersX-Content-Type-Options: nosniff, X-Frame-Options: DENY, Referrer-Policy, Permissions-Policy on every response. A full Content-Security-Policy is available but opt-in (see §6).headers on, CSP off
3Require-login-for-readsWhen enabled, every /api/* route (except the login flow itself) requires a valid session. Off by default — see §8 for exactly what that means today.opt-in, off
Read this before a production rollout

Every read (GET) route is public by default. Every state-changing route (POST) is gated per-route with an explicit RBAC dependency. Set VULNHUNTER_REQUIRE_LOGIN_FOR_READS=true to close the read gap — it requires a real, stable VULNHUNTER_SESSION_SECRET as a precondition (checked at startup). Independently, set VULNHUNTER_PRODUCTION=true to enforce that same real-secret requirement unconditionally, even on a deployment that leaves the read gap open — the two flags are separate axes, not one gating the other.

03Data & storage model

Pipeline output and admin-editable policy stay as files; the record stores that see real read-modify-write traffic — approvals, exceptions, audit/AI-usage logs, asset ownership, user accounts — now live in a real local SQLite database, accessed through SQLAlchemy Core so a future move to Postgres for multi-tenancy is a connection-string change, not a rewrite.

PathWhat lives there
remediation/output/normalized-findings.jsonEvery finding, in the one common schema (§4) — the system of record.
REMEDIATION_PLAN.mdA point-in-time snapshot: risk tier, action type, rollback plan per finding, written by the remediation-planner subagent.
remediation/output/*.ymlGenerated Ansible playbooks, one per remediable finding.
remediation/vulnhunter.dbShared local SQLite database (gitignored) — approvals, exceptions, activity/AI-usage logs, asset ownership, user accounts, notification-scheduler dedup state, and pending live-data adapter output all live here now, one table each.
remediation/config/*.yamlEvery admin-editable policy: priority weights, SLA windows, remediation policy per asset domain, risk-scoring weights, exposure-score weights.
remediation/live-data/*Raw CSV/XML exports written by a CVE-scoped connector's Fetch action (Tenable/Qualys/OpenVAS) before ingestion via /remediate.

Why a real database for the record stores, files for the rest

Pipeline output (findings, the plan, generated playbooks) and admin policy stay as files — human-readable, diffable in git, inspectable without a DB client, a deliberate fit for artifacts whose whole point is being reviewable. The record stores above moved to SQLite specifically because each one is genuinely mutated by concurrent requests (an approval decision, an exception revoke, a login), and a flat-file read-modify-write cycle under real concurrency can silently drop a write. remediation/utils/file_lock.py (a real cross-platform advisory file lock with a timeout, not a placeholder) still guards each store's own multi-statement critical section — SQLite's own locking gives atomicity for a single statement, but a caller whose critical section spans more than one (compute-next-id-then-insert) still needs its own mutual exclusion. The honest cost that remains: no historical trend storage yet (every chart is a live snapshot, not a time series) and single-node deployment only — this is a real SQLite file on one machine, not a distributed database. This is the top item on VulnHunter's own roadmap (§8).

Data handling & residency (SaaS target design)

Everything in this subsection is a target design for a possible future hosted "VulnHunter Cloud" tier — proposed, not built. Stated plainly first: the current reality, per the storage-model table above and dashboard/README.md, is that VulnHunter persists its record stores in a real local SQLite database and everything else in flat JSON/YAML files, all on whatever single host runs it, with no encryption-at-rest layer of its own — it inherits whatever the host filesystem/disk provides. For today's single-host deployment model, that's the correct place for this control to live: enable your OS's or cloud provider's disk-level encryption (BitLocker, LUKS, or your cloud disk/volume's default encryption-at-rest option) under the host this app runs on, and every file VulnHunter writes — the SQLite database included — inherits it transparently, with no code change and no key-management story this app would need to invent. The app layer already avoids the one thing that would need its own encryption regardless of disk-level coverage: passwords are one-way PBKDF2-HMAC-SHA256 hashes (see "Authentication & sessions" below), never stored in any recoverable form. Transit encryption has two real paths today, not zero: local/dev HTTPS is built in (uvicorn's native TLS, opt-in per run via the SSL_KEYFILE/SSL_CERTFILE env vars — see dashboard/README.md), and a real deployment should still terminate TLS at a reverse proxy with a CA-issued certificate in front of it (the same doc's nginx/Let's Encrypt example) rather than running a self-signed cert in production. None of the AES-256/CMK/key-rotation controls below exist yet; they are what a hosted, multi-tenant offering would need to build on top of the disk-level encryption that's already the right answer for a self-hosted deployment today.

Framing: 2026 SOC 2 best-practice guidance for SaaS data handling

The controls below track common 2026 SOC 2 best-practice guidance for a multi-tenant SaaS platform — encryption at rest and in transit, documented key rotation, data-residency commitments, and tested backup/DR — rather than a specific numbered control framework VulnHunter has been audited against.

ControlTarget design
Encryption at restAES-256 across the primary data store, backups, logs, and any analytics store.
Encryption in transitTLS 1.3 enforced at the edge for every browser, connector, and API connection — not operator-dependent, as it is today.
Key rotationA documented, scheduled key-rotation policy — not a one-time key set at provisioning.
Customer-managed keys (CMK)A possible enterprise-tier differentiator: the customer holds the decryption key, and VulnHunter's hosting provider cannot read that customer's data without their cooperation. Not yet decided as a committed, shipping feature.
Data residencyAll copies of a customer's data — primary store, backups, logs, analytics/aggregation stores, and any support-access copy — stay within that customer's approved region. Residency policy reviewed at least annually, or immediately after any significant architecture or regulatory change.
Backups & DRRegular automated backups, with periodically tested restores (an unrestored backup isn't a verified one). Specific RPO/RTO targets per tier are a decision for whoever builds this, sized to whatever uptime commitments docs/PRICING.md settles on — not invented here.
Multi-tenant isolation — today vs. target, stated honestly

VulnHunter's current RBAC (§6) is tenant-label filtering, not hardened multi-tenant data isolation: the MSSP "tenant view" is a client-side filter over one shared dataset, and server-side team-scoping narrows a non-admin's queries — but every tenant and team reads from the same underlying file store. The RBAC, Multi-Tenancy & Governance document §02 already names the standards a real implementation would need to satisfy (NIST SP 800-53 AC-3/AC-4/AC-6, OWASP API Security Top 10:2023 API1, OWASP Top 10:2025 A01, OWASP ASVS 5.0 V8 §8.3.1). True SaaS multi-tenancy — most plausibly a database with a real per-tenant boundary — is a target-state architecture change for this hosted design, not something to bolt onto the current file-based model incrementally, and not yet built.

See docs/PRICING.md's "Deployment & Hosting" section for the corresponding illustrative infrastructure cost model, and the RBAC, Multi-Tenancy & Governance document for the full current-state access-control picture this subsection builds on.

04The Finding schema

Every connector — Tenable, Qualys, OpenVAS/GVM, Prisma Cloud, Cortex XSIAM, Infoblox, Axonius, Active Directory, or a generic webhook — maps its own export format into exactly this shape. Nothing downstream (scoring, enrichment, planning, the dashboard) ever needs to know a source-specific field name again.

{
  "id": "FIND-1",
  "source": "tenable | qualys | openvas | prismacloud | cortex-xsiam | armis | threat-intel",
  "source_ref": "<plugin/QID/OID/device ID from the origin system>",
  "asset": {
    "name": "WIN-DC01", "ip": "10.20.30.41",
    "type": "windows-server | unix-server | network-security-device | ... (17 types)",
    "os": "Microsoft Windows Server 2019 Datacenter"
  },
  "title": "MS Windows Print Spooler RCE (PrintNightmare)",
  "cve": "CVE-2021-34527",           // nullable — policy/config findings often have none
  "cvss": 8.8,
  "severity": "Critical | High | Medium | Low",
  "remediation_domain": "windows-server | unix-server | iot-ot-device | null",
  "first_seen": "2026-07-28", "last_seen": "2026-08-02",
  "kev": { "listed": true, "date_added": "2021-11-03", "known_ransomware_campaign_use": "Known" },
  "epss": { "score": 0.9976, "percentile": 0.9996 },
  "poc_available": true, "user_interaction_required": false
}

Why asset.type is the routing key

It decides which remediation-fixer subagent — if any — can turn this finding into a real remediation artifact. Today, windows-server and unix-server have a working fixer that generates a playbook, iot-ot-device has one that generates a compensating-control recommendation instead, and application findings with a CVE (the SCA case) get a dependency-upgrade plan (see the Remediation Engine document's "Four remediation tracks"). Every other type (17 in total, spanning network gear, cloud infrastructure, certificates, AI/ML findings, code repositories, and more) is still normalized, scored, and planned — just routed to "no automated fixer yet, here's who should own it" instead of a generated artifact.

kev / epss are added later, not at ingestion

A dedicated enrichment stage populates these from live public feeds (CISA KEV, FIRST.org EPSS) after normalization. Both are null whenever cve is null — KEV/EPSS are inherently CVE-scoped, so a policy finding with no CVE honestly carries no exploitation signal rather than a guessed one.

06Security architecture

Authentication & sessions

Local email/password accounts, hashed with PBKDF2-HMAC-SHA256. Sessions are a signed cookie (vulnhunter_session) verified against VULNHUNTER_SESSION_SECRET. Optional OIDC/SSO support exists and is exposed on the login page only when a real provider's OIDC_ISSUER/OIDC_CLIENT_ID/OIDC_CLIENT_SECRET are configured — otherwise the button is simply absent, not stubbed.

Roles & team scoping — the real model, not an idealized one

This is intentionally simple: one boolean, admin or not. Every mutation route requires at minimum a logged-in session; most require role == "admin" outright. A second, independent axis — team — narrows which findings and approvals a non-admin user's own queries return, enforced server-side per request. There is no granular permission matrix (no separate "analyst," "approver," "read-only" roles) — see the RBAC, Multi-Tenancy & Governance document for what this means in practice and its honestly-disclosed limits.

The execution boundary — the single most important design decision

Verbatim, because it is load-bearing

"Nothing in this repository ever executes against real infrastructure automatically — by construction, not by policy." The subagents that draft Ansible playbooks are given Read, Write tool access only in their own frontmatter — no Bash, no network tool, no credentials. They cannot reach a host even if a prompt somehow told one to. Every generated playbook is a reviewable artifact for a human, or your own change-managed automation platform, to run.

07Frontend architecture

A hand-rolled single-page app — no React, no build step, no bundler. Deliberate: the environment this was built in had no Node/npm runtime available to compile or verify a framework-based frontend against, and shipping unverifiable code is a worse outcome than a plainer one that's actually been run.

  • Router: a regex-pattern table (app.js) maps a URL path to a page module — around 50 routes today.
  • Page module convention: every pages/*.js file exports title and an async render(container) — it owns its own markup, its own api.js calls, and its own event wiring.
  • Shared libraries: api.js (every backend call in one place), dom.js (escaping, flash messages, KPI-card helpers), charts.js (bar/pie SVG, shared severity palette), rbac-aware helpers for showing/hiding admin-only controls client-side (never the actual security boundary — that's always enforced server-side too).

08Honest current-state limits

Every enterprise reference in this suite says plainly where the product is today versus where a production rollout would need to invest further. Reused consistently across all eight documents:

Single-tenant, single-node

A real local SQLite database now backs the record stores, but it's one file on one machine with no per-tenant data boundary. The MSSP "tenant switcher" in the UI is an illustrative client-side filter over one shared dataset — not real per-tenant isolation. See the RBAC/Governance document.

Reads are public by default

Every GET route is open unless VULNHUNTER_REQUIRE_LOGIN_FOR_READS is explicitly set — a deliberate MVP default, not a bug, but one to close before a real rollout.

Synchronous pipeline execution

A pipeline run blocks the request that started it. A production deployment needs a real job queue behind long-running operations (scans, large-tenant exports).

No historical trend storage

Every chart is a live, current-moment snapshot — there is no daily-snapshot table yet, so "trend over time" views are honestly absent rather than faked.
