02The connector contract

Every pull connector — 8 of them today — implements the same small surface, so a reviewer already knows the shape before opening the file:

# The pattern every connector follows
class SomeConnector:
    def __init__(self, ...credentials..., session=None):
        self.session = session or requests.Session()  # DI seam for tests

    def test_connection(self):
        """Cheapest real authenticated call - no confirm gate needed."""

    def fetch_and_write_csv(self, output_path):
        """Real fetch, confirm-gated at the route level, never here."""

Credentials are always a constructor argument, never a stored setting. A stateful-protocol connector (LDAP, GMP) takes an injectable connection/gmp_client parameter instead of a requests.Session — same seam, different transport.

03Adding a new connector — the real checklist

1

Write the connector module

remediation/connectors/<name>_connector.py — test_connection() + a fetch method, against the vendor's real, publicly documented API.

2

Decide the output shape

CVE-scoped host source → flatten into tenable_connector.CSV_FIELDNAMES (reuse the existing normalizer). Already-typed posture source → normalize directly to the Finding schema. Asset-only source → the shared asset-inventory shape.

3

Unit-test against a hand-rolled fake

Not the vendor SDK's own mock utilities — a minimal fake object recording calls and returning canned, documentation-shaped responses. Cover: auth header/payload construction, response parsing, the confirm-gate boundary.

4

Add two dashboard routes

POST /api/<name>/test-connection (no confirm, rbac.require_admin) and POST /api/<name>/fetch (confirm-gated, returns a preview_only response when unconfirmed).

5

Wire the frontend

Add functions to api.js, a catalog entry to adaptorCatalog.js, a page module under pages/, and a route in app.js's router table.

6

Disclose the verification status honestly

"Built against public docs, unit-tested against mocked responses, never exercised against a real account" is the default and expected state for a new connector — say so directly in the module docstring and the dashboard page.

04Subagent conventions

Every subagent is a markdown file with YAML frontmatter declaring its allowed tools. This is the actual enforcement mechanism behind "never executes against real infrastructure" — not a runtime check, a capability the subagent simply doesn't have.

SubagentToolsWhy
remediation-fixer-windows/-unixRead, WriteDrafts a playbook; cannot run one — no Bash, no network, no credentials
remediation-fixer-otRead, WriteSame restriction, different artifact shape — a compensating-control recommendation, never a patch script (OT devices are rarely safe to patch live)
remediation-fixer-applicationRead, WriteDrafts a dependency-upgrade plan (remediation/output/upgrade-plans/<id>.json); cannot edit a manifest, run a package manager, or open a PR itself
remediation-fixer-codeRead, WriteDrafts a unified diff for a first-party code finding (remediation/output/code-fixes/<id>.json, with a validation record); Python in remediation/gitops/ checks and applies it, and only the finding's own file may change
vuln-scannerRead, Grep, Glob, BashNo Edit/Write — physically cannot modify what it's scanning
vuln-triage-reporterWriteProduces a report only
vuln-fixerRead, Edit, Write, BashNew-branch-only git workflow; never commits to main
vuln-verifierRead, Grep, Glob, BashSame read-only shape as vuln-scanner — re-checks a fix via git show/git grep against a named branch, never checks that branch out
The rule for any new fixer-shaped subagent

If it drafts a change to real infrastructure config, it gets Read, Write only. This is the one convention in this codebase that is never relaxed for convenience.

05Testing conventions

  • Python: python -m unittest discover -s tests -p "test_*.py" — 1,933 tests today, all passing; one file per module/route group, hand-rolled fakes over vendor mock libraries.
  • Test files for the newer modules: tests/test_guidance.py, test_scanner_ingest.py (SARIF, coverage, CI/CD checks), test_client_controls.py, test_ai_usage.py, test_threat_models.py, test_grc.py and test_hunting.py. Each runs against a temporary database and fakes, with no network and no model call.
  • JS: node --check <file> catches syntax errors only — a passing check is necessary, never sufficient. Frontend behavior is verified live in a running browser, not assumed from source reading.
  • CI: GitHub Actions runs the full Python suite on every push. A clean local pass can still mask an environment-specific failure (see the CLI's own dry-run-ordering bug, fixed after reproducing it in a simulated clean environment) — reproduce, don't assume.

# Preview only - never calls the API
python cli/quanta.py /quanta-scan ./target --dry-run

08Health checks & operational monitoring

A real, machine-readable health/status endpoint exists — every field below is an actual checked fact at request time, not a hardcoded "OK":

# Open by default (see the auth note below) - no credentials needed. -k accepts the
# local self-signed HTTPS cert this app now generates on first run (see the "HTTPS"
# section of dashboard/README.md) - a real deployment behind a CA-issued cert doesn't need it.
curl -k https://127.0.0.1:5050/api/status
FieldWhat it actually reports
status"ok" or "degraded" — degraded only when something genuinely load-bearing (the remediation findings or playbooks files) fails to read. A missing SMTP config or session secret is an expected, disclosed MVP default, not degradation, and never flips this.
app_versionThe FastAPI app's own declared version string — the same value shown in the dashboard's page footer.
uptime_secondsReal process uptime from a monotonic clock (immune to system clock changes) — resets to zero on every restart; there's no persistence layer behind it.
quanta_scan_findings / remediation_findings / remediation_playbooksLive counts re-read from disk at request time, never cached.
smtp_configured / session_secret_configuredWhether the corresponding environment variables are actually set — never fabricated as "configured."
threat_intelFreshness of the KEV/EPSS enrichment data on disk, with its own available flag and error string if that check itself failed.
notification_scheduler_aliveWhether the background scheduler task (report/alert checks) is still running in this process. With several replicas only the elected leader runs it; quanta_scheduler_leader in /metrics shows which.
data_storesPer-store exists / last_modified / record_count for four of the tables in the database (the gitignored local SQLite file by default, PostgreSQL when QUANTA_DATABASE_URL is set) (exceptions, remediation approvals, activity log, AI usage log) — a corrupt/unreadable table reports its own error string instead of taking down the whole check.
Auth is conditional, not absent

/api/status is open with no session by default, same as every other read route in this MVP. If a deployment sets QUANTA_REQUIRE_LOGIN_FOR_READS=true, this route is not in the small allow-list of routes the login flow itself needs (/api/auth/*) — so it starts requiring a valid session too. Account for that in your uptime monitor's own auth if that flag is on.

Orchestrators use the separate probes /healthz (liveness), /readyz (readiness) and /metrics (token-protected, includes quanta_jobs_queued, quanta_jobs_dead and quanta_scheduler_leader), defined in dashboard/observability.py; /api/status remains the human-facing status surface and already covers version. For a check outside this endpoint: the notification scheduler's own due-check logic is independently callable on demand via POST /api/notification-settings/run-checks-now, useful for confirming that background loop is actually reachable rather than only trusting notification_scheduler_alive.

09Queue jobs & running the worker

Scheduled and manual connection syncs are rows in the jobs table, not threads. A worker claims a job (SELECT ... FOR UPDATE SKIP LOCKED on PostgreSQL), heartbeats while it runs, and the job is re-offered after the visibility timeout if the worker dies. Failures retry with backoff and a job is marked dead after 3 attempts.

# Dedicated worker (the web process also runs an embedded one unless QUANTA_EMBEDDED_WORKER=false)
python cli/quanta_admin.py worker

# Inspect the queue (also GET /api/admin/jobs)
python cli/quanta_admin.py jobs

# First-run setup, once per release, under a lease
python cli/quanta_admin.py prepare
1

Write an idempotent handler

Delivery is at-least-once, so a handler must be safe to run twice. Register it by job type in remediation/coordination/worker.py.

2

Enqueue with a dedupe key

Call the enqueue function in jobs.py with a dedupe key so two replicas (or a double click) do not queue the same work twice.

3

Test against SQLite

The queue logic runs on SQLite in the test suite; the SKIP LOCKED claim path is PostgreSQL only and is covered by unit tests, not yet by a live multi-replica run.

Set QUANTA_LOCK_BACKEND=db when running more than one replica so FileLock uses database leases, and QUANTA_LEADER_TTL_SECONDS to tune scheduler failover.

10Push connections & API-key-guarded routes

Push connections. ServiceNow, Jira and Splunk are stored in Connections like pull sources, each with a rule (min_severity, kev_only, min_epss, max_per_run). To add one, implement it in remediation/connections/push.py, register it in registry.py, and keep ticket creation idempotent through the finding-to-ticket links in links.py (table ticket_links). Ticket state is read back and mirrored onto the finding's assignment (ServiceNow state 1..8, Jira status category).

API-key-guarded routes. Inbound machine routes (POST /api/ingest/findings, POST /api/ingest/scanner-csv, POST /api/inbound/ticket-status, GET /api/export/findings) use Quanta-issued keys from remediation/apikeys/store.py: qk_<prefix>_<secret>, SHA-256 hash only, scopes ingest:write / tickets:update / read:findings, expiry, revocation, rate limit QUANTA_API_KEY_RATE_MAX. Only paths under /api/ingest/, /api/inbound/ and /api/export/ are exempt from the login gate, so a new key-guarded route must live under one of those prefixes and check its required scope. Pushed findings are validated by remediation/ingest/api_findings.py (identity = source + asset + source_ref + CVE; reconcile only for complete exports). GET /api/connections/schema returns a JSON Schema for every connection type. See docs/INTEGRATION_API.md.

11Adding guidance, a control test, a hunt technique or a runbook

These four extensions are data or a few lines of code, each with a matching test file. None calls a model, so the result is the same every run and can be reviewed in git.

A guidance entry

1

Add the entry

Append to entries: in remediation/guidance/knowledge.yaml: id, title, match (any of cwe, keywords, scan_types, asset_types), summary, why, ordered steps, verify, compensating, effort and references. Keep steps concrete and tool-neutral, and never invent a CVE-specific fix here.

2

Know how it is matched

engine.py matches by CWE first, then scan type and keywords, then asset type, and adds what it knows about the specific finding (package and fixed version, operating system, KEV status, the client's recorded controls). The file is read live.

3

Test

Add a case to tests/test_guidance.py that builds a finding with the CWE or keyword and asserts the entry is chosen.

A control test

1

Write the check

In remediation/grc/evidence.py, add a function t_something(c) that reads the shared Context (c.findings, c.engine, c.t thresholds) and returns _res(result, metric, threshold, detail), where result is pass, fail, warn or na. Return na when there is too little data; never return pass on no data. Register it in the TESTS dict under a test id with a title.

2

Set the threshold and the mapping

In remediation/config/grc_tests.yaml, add any threshold under thresholds and map the test id under mappings to the framework controls it is evidence for (for example nist-800-53-r5: [RA-5]). A test with no mapping still runs but supports no control.

3

Test

Add cases to tests/test_grc.py for pass, fail and the na path. Results are evidence that Quanta observed something, not an audit conclusion; keep detail strings worded that way.

A hunt-library technique

1

Add the technique

In remediation/hunting/library.yaml, add a key for an ATT&CK technique id that Quanta tags, with hunt (title), data_sources, one or more detections (each a name and a Sigma-style selection) and notes. Selections use field names with the modifiers contains, startswith and endswith; a list means OR, several fields mean AND.

2

Know the limit

translate.py renders the selection as Splunk SPL. It is a small translator, not pySigma, and raises on an unsupported modifier or field name. Quanta never runs the query: the analyst maps field names to their own data model, runs it, and records the result.

3

Test

Add a case to tests/test_hunting.py that generates a hunt for a finding carrying the technique and checks the rendered query.

A runbook

Add an entry to remediation/hunting/runbooks.yaml with id, title, techniques, keywords and ordered steps. triage.py picks a runbook by the alert's technique first, then by title keywords, and falls back to the generic runbook. Runbooks are shown to responders; execution stays with the customer's own tools. Cover a new entry in tests/test_hunting.py.

12Git hosts, the gitops policy and the AppSec config files

The fix pull-request workflow is deliberately split: a model may write a plan or a diff as a file, and plain Python does everything that touches a repository. Keep that split when you extend it.

Adding a Git host connector

1

Implement the host client

In remediation/connectors/git_host_connector.py, add a class beside GitHubConnector and GitLabConnector with the same methods (whoami, test_connection, branch_sha, create_branch, get_file, commit_files, open_change_request, get_change_request) and add it to build(). Take the HTTP session as a constructor argument so tests can inject a fake. Refuse the default branch in the client itself, and do not retry a write (a retried write could open a second pull request).

2

Register it as a tool connection

In remediation/connections/registry.py, add a spec the way _git_spec() does for github and gitlab: kind tool (used on demand, not synced), the token as a secret field, and the base URL listed under safe_targets so it passes url_safety before anything is constructed.

3

Test against a fake and disclose

Unit-test against a hand-written fake session (see tests/test_gitops.py). State in the docstring and the docs that it was built to public documentation and never run against a live host.

The gitops policy

remediation/config/gitops_policy.yaml is read by remediation/gitops/policy.py on each use. It holds the branch template and protected-branch patterns, commit style, pull-request labels, reviewers and the provenance text appended to every description, whether a lock file forces a draft, whether approval is required before opening (and whether the approver must differ from the proposer), file limits, the denied paths (.github/**, CODEOWNERS, keys, env files and pipeline definitions), and the process steps shown on the page. Per-repository changes go under overrides, matched by a glob on the repository path. Loosening a guard here is an organisational decision; do not add a code path that bypasses policy.py, and keep proposals.open_pr the only function that writes to a repository.

The Git host webhook, scheduled sync and demo data

Relationship graphs. remediation/graphs/ holds one builder per module (soc, appsec, devsecops, infra, ai, remediation, grc, admin), each build(engine=None, findings=None, **context) returning the shape in schema.py through GraphBuilder (deterministic, capped at 400 best-connected nodes, an honest empty state with a note, never an invented node). GET /api/graphs/<module> in dashboard/app.py calls it with the team-scoped findings; the browser draws it with graphView.js and computes clusters, shortest routes, betweenness, articulation points, PageRank and loops with graphTheory.js (pure, tested under Node). To add one: write the builder and its test, register the id in __init__.py, add a /api/graphs/<id> line to licensing.yaml, and add the menu and catalog entries in both nav.js and capabilities.yaml.

remediation/gitops/webhooks.py verifies deliveries for POST /api/inbound/git-webhook (in dashboard/appsec_api.py): GitHub's X-Hub-Signature-256 HMAC-SHA256 of the body, or GitLab's X-Gitlab-Token, compared in constant time against QUANTA_GIT_WEBHOOK_SECRET (QUANTA_GIT_WEBHOOK_SECRET_FILE for a mounted secret). It is the one inbound route exempt from both the login gate and API keys, so keep it that way only while the signature check stays first: no secret means 503, a bad signature 401, and an unknown pull request is ignored. Test with hand-signed payloads (tests/test_gitops_automation.py). The hourly scheduler tick follows open pull requests and re-checks merged ones, controlled by QUANTA_GITOPS_SYNC (default true; false, 0 or no disables it) and builds no connector when none is open. python cli/quanta_admin.py seed-appsec-demo [--name NAME] [--remove] registers a demo application from the sample SBOM plus five findings under the source appsec-demo (remediation/appsec/demo.py); --remove undoes exactly those, and it prints the network_topology.yaml entry for the exposure lane.

Subagent tool scoping for this area

remediation-fixer-application and remediation-fixer-code hold Read, Write only. Do not give either Bash or Edit so that it can "just open the pull request": the checking, applying and host access live in Python (diffing.py, upgrade.py, proposals.py) precisely so they can be tested and so the model cannot reach a repository.

Routes and tests

The routes live in dashboard/appsec_api.py, an APIRouter built by build_router() with the app's dependencies (API-key guard, team scoping, upload reader) injected, which keeps it out of app.py. A route that machine callers use must sit under /api/ingest/, /api/inbound/ or /api/export/ or be one of the existing gate routes, and check its scope with require_api_key. Tests are in tests/test_appsec_analysis.py, test_appsec_api.py, test_appsec_sbom.py and test_gitops.py, with shared fixtures in tests/appsec_fixtures.py.
