Developer Guide

The building blocks this codebase is actually made of — where things live, the one contract every connector follows, and how to extend the product without breaking its safety guarantees.

02The connector contract

Every pull connector — 8 of them today — implements the same small surface, so a reviewer already knows the shape before opening the file:

# The pattern every connector follows
class SomeConnector:
    def __init__(self, ...credentials..., session=None):
        self.session = session or requests.Session()  # DI seam for tests

    def test_connection(self):
        """Cheapest real authenticated call - no confirm gate needed."""

    def fetch_and_write_csv(self, output_path):
        """Real fetch, confirm-gated at the route level, never here."""

Credentials are always a constructor argument, never a stored setting. A stateful-protocol connector (LDAP, GMP) takes an injectable connection/gmp_client parameter instead of a requests.Session — same seam, different transport.

03Adding a new connector — the real checklist

1

Write the connector module

remediation/connectors/<name>_connector.py — test_connection() + a fetch method, against the vendor's real, publicly documented API.

2

Decide the output shape

CVE-scoped host source → flatten into tenable_connector.CSV_FIELDNAMES (reuse the existing normalizer). Already-typed posture source → normalize directly to the Finding schema. Asset-only source → the shared asset-inventory shape.

3

Unit-test against a hand-rolled fake

Not the vendor SDK's own mock utilities — a minimal fake object recording calls and returning canned, documentation-shaped responses. Cover: auth header/payload construction, response parsing, the confirm-gate boundary.

4

Add two dashboard routes

POST /api/<name>/test-connection (no confirm, rbac.require_admin) and POST /api/<name>/fetch (confirm-gated, returns a preview_only response when unconfirmed).

5

Wire the frontend

Add functions to api.js, a catalog entry to adaptorCatalog.js, a page module under pages/, and a route in app.js's router table.

6

Disclose the verification status honestly

"Built against public docs, unit-tested against mocked responses, never exercised against a real account" is the default and expected state for a new connector — say so directly in the module docstring and the dashboard page.

04Subagent conventions

Every subagent is a markdown file with YAML frontmatter declaring its allowed tools. This is the actual enforcement mechanism behind "never executes against real infrastructure" — not a runtime check, a capability the subagent simply doesn't have.

SubagentToolsWhy
remediation-fixer-windows/-unixRead, WriteDrafts a playbook; cannot run one — no Bash, no network, no credentials
remediation-fixer-otRead, WriteSame restriction, different artifact shape — a compensating-control recommendation, never a patch script (OT devices are rarely safe to patch live)
remediation-fixer-applicationRead, WriteDrafts a dependency-upgrade plan; cannot edit a manifest, run a package manager, or open a PR itself
vuln-scannerRead, Grep, Glob, BashNo Edit/Write — physically cannot modify what it's scanning
vuln-triage-reporterWriteProduces a report only
vuln-fixerRead, Edit, Write, BashNew-branch-only git workflow; never commits to main
vuln-verifierRead, Grep, Glob, BashSame read-only shape as vuln-scanner — re-checks a fix via git show/git grep against a named branch, never checks that branch out
The rule for any new fixer-shaped subagent

If it drafts a change to real infrastructure config, it gets Read, Write only. This is the one convention in this codebase that is never relaxed for convenience.

05Testing conventions

  • Python: python -m unittest discover -s tests -p "test_*.py" — one file per module/route group, hand-rolled fakes over vendor mock libraries.
  • JS: node --check <file> catches syntax errors only — a passing check is necessary, never sufficient. Frontend behavior is verified live in a running browser, not assumed from source reading.
  • CI: GitHub Actions runs the full Python suite on every push. A clean local pass can still mask an environment-specific failure (see the CLI's own dry-run-ordering bug, fixed after reproducing it in a simulated clean environment) — reproduce, don't assume.

06CLI usage

# Preview only - never calls the API
python cli/vulnhunter.py /vulnhunt ./target --dry-run

# Real run, explicit spend cap (default $2.00)
python cli/vulnhunter.py /remediate --generate --max-budget-usd 5.00

The dashboard's /run page is a thin UI over this exact same entry point — same dry-run default, same confirm gate, same budget cap.

08Health checks & operational monitoring

A real, machine-readable health/status endpoint exists — every field below is an actual checked fact at request time, not a hardcoded "OK":

# Open by default (see the auth note below) - no credentials needed. -k accepts the
# local self-signed HTTPS cert this app now generates on first run (see the "HTTPS"
# section of dashboard/README.md) - a real deployment behind a CA-issued cert doesn't need it.
curl -k https://127.0.0.1:5050/api/status
FieldWhat it actually reports
status"ok" or "degraded" — degraded only when something genuinely load-bearing (the remediation findings or playbooks files) fails to read. A missing SMTP config or session secret is an expected, disclosed MVP default, not degradation, and never flips this.
app_versionThe FastAPI app's own declared version string — the same value shown in the dashboard's page footer.
uptime_secondsReal process uptime from a monotonic clock (immune to system clock changes) — resets to zero on every restart; there's no persistence layer behind it.
vulnhunt_findings / remediation_findings / remediation_playbooksLive counts re-read from disk at request time, never cached.
smtp_configured / session_secret_configuredWhether the corresponding environment variables are actually set — never fabricated as "configured."
threat_intelFreshness of the KEV/EPSS enrichment data on disk, with its own available flag and error string if that check itself failed.
notification_scheduler_aliveWhether the in-process background scheduler task (report/alert checks) is still running.
data_storesPer-store exists / last_modified / record_count for four of the tables in the gitignored local SQLite database (exceptions, remediation approvals, activity log, AI usage log) — a corrupt/unreadable table reports its own error string instead of taking down the whole check.
Auth is conditional, not absent

/api/status is open with no session by default, same as every other read route in this MVP. If a deployment sets VULNHUNTER_REQUIRE_LOGIN_FOR_READS=true, this route is not in the small allow-list of routes the login flow itself needs (/api/auth/*) — so it starts requiring a valid session too. Account for that in your uptime monitor's own auth if that flag is on.

There is no separate /health, /api/health, or /api/version route — /api/status is the one real health surface, and it already covers version. For a check outside this endpoint: the notification scheduler's own due-check logic is independently callable on demand via POST /api/notification-settings/run-checks-now, useful for confirming that background loop is actually reachable rather than only trusting notification_scheduler_alive.
