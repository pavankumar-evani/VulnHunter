Connectors & Adaptors Catalog

One consolidated hub for every system Quanta can pull from, push to, or scan directly — organized honestly by what's actually working versus what's researched and ready to build next.

01The Adaptors hub

Every connector below is a risk-management decision, not just a technical integration — this is the only way real vulnerability, asset, and threat data enters Quanta's pipeline at all. The seven-stage remediation lifecycle (documented in the Remediation Engine & Workflows document) only ever sees what a connected source actually reported: an unconnected scanner, an unconfigured CNAPP, or an asset-discovery source nobody wired up is a coverage gap in your risk picture, not a limitation of the scoring or planning logic downstream of it. How current and complete that picture is — and how much the KEV/EPSS-aware prioritization described in the Vulnerability Finding Engine document is protecting against real, live threats rather than a stale snapshot — depends entirely on which of the sources below are actually connected in your environment.

Every integration lives in one place (/adaptors), filterable by category, with a two-tier honesty label instead of a single "supported" checkmark:

live

A real, working connector class + a real dashboard page — Test Connection, Fetch/Send, or (for the scan engine) the full scan lifecycle.

reference

Real, researched facts about the vendor's actual API — auth model, real endpoint shape, what data would flow — with no working code behind it yet.

AI-usage connectors: counts only, and never run against a live account

remediation/connectors/ai_usage_connector.py holds both provider connectors. They are stored connections on the Connections page (output type ai-usage), pulled on a schedule as queued jobs, and they return aggregated daily buckets keyed so a re-pull updates rather than doubles. Quanta stores token counts, model, time and workspace or project attribution only, never prompts or responses. Both were built against the providers' published documentation and unit-tested against hand-written responses; neither has been exercised against a live Anthropic or OpenAI account, and each provider's schema evolves, so check field names against your own account first. Cost is reported, estimated from ai_pricing.yaml (which ships empty) or shown as unknown, never as zero.

A fourth path: findings pushed in, not pulled out

remediation/connectors/generic_connector.py is a different shape from every connector above — the receiving side of a webhook, for any SIEM/XDR/EDR/SOAR tool that already supports posting a custom outbound webhook. Quanta never calls out; the outside tool calls POST /api/ingest/generic with a JSON body validated against a minimal required shape (title, severity, asset_name, asset_type) and normalized into the same Finding schema every other source uses. One real, generic, testable adapter instead of another bespoke vendor connector nobody has real API access to verify.

Unauthenticated unless production mode is on

Unlike every connector above, this route is not gated behind rbac.require_admin or any browser session — a machine-to-machine webhook receiver. With QUANTA_PRODUCTION=true it now requires a Quanta API key with the ingest:write scope (see §08); in a default, non-production run it still accepts anonymous posts, throttled per IP (see §05). Its output file is not capped in total size over time, a disclosed follow-up. New integrations should use the keyed POST /api/ingest/findings endpoint in §08 instead, which updates in place and reports bad records individually.

03Push connectors — findings out

Every push connector shares the same preview-then-confirm shape: build the exact real payload, show it, require an explicit confirm before anything is actually sent — no accidental ticket storms.

Stored push connections: rules, idempotency and state read-back

Besides the one-off page above, an admin can store a ServiceNow, Jira Cloud or Splunk connection on the Connections page and let it run on a schedule. Each carries a rule that decides which findings become tickets:

FieldMeaningDefault
min_severitySend findings at or above this severityHigh
kev_onlyOnly findings on the CISA KEV listoff
min_epssOnly findings with at least this exploit probability (0 to 1)none
max_per_runMost tickets per run, so a first sync cannot flood the service desk50

Each run picks matching findings not yet pushed through that connection, most urgent first (KEV, then EPSS, then severity). ServiceNow incidents are keyed on correlation_id, Jira issues on a quanta-<finding id> label, and Splunk receives each finding once, so a re-run never duplicates. One failing finding does not stop the batch; its error is kept on its link and retried next run.

Quanta keeps a link between each finding and its ticket and, on every run, reads the current state of the open ones back and maps it to its four work states:

Quanta stateServiceNow stateJira status category
open1 (new)new
in progress2indeterminate
blocked3, 4, 5 (on hold / awaiting)(custom workflow dependent)
resolved6, 7, 8 (resolved / closed / cancelled)done

If the finding has an assignment, its work status follows. A resolved ticket marks the assignment resolved; it never closes the finding, because the next scan decides whether the vulnerability is really gone. The finding's detail view lists its tickets and their state.

04Connecting a source — the admin walkthrough

This is the real, current path for an admin turning on an already-built source — not a developer wiring up a brand-new connector class (see the Developer Guide document's connector contract for that). All 11 connector pages with a real form — the 8 Test Connection/Fetch pages above plus ServiceNow/Jira/Splunk — follow the exact same shape:

StepWhat actually happens
1 · Open the connector's pageFrom /adaptors filtered by category, or directly (e.g. /tenable, /servicenow). Every real action below requires being logged in as admin — enforced server-side by rbac.require_admin, not just a hidden button.
2 · Enter credentialsDirectly into that page's form — e.g. Tenable's access key + secret key, generated from the vendor's own console. Typed fresh every visit on a connector's own page, which saves nothing. To keep it for scheduled syncs, add it on the Connections page instead (needs QUANTA_ENCRYPTION_KEY).
3 · Test ConnectionOne click, no confirm checkbox needed. Calls the vendor's cheapest real authenticated endpoint — Tenable's is GET /session, its lightest documented call — so a bad credential pair fails in under a second, before anything slower runs.
4 · Check the confirm box, then Fetch (or Send)The real action: a live export, scan, or send. Gated behind an explicit checkbox because it's a real call against a real production system — every push connector additionally shows you the exact payload for free before this step.
5 · See what landedDiffers by source category — see below.

Where the data actually goes

What "Fetch" produces depends on which source category a connector belongs to (full detail in the Vulnerability Finding Engine document's source taxonomy, §01):

  • CVE-scoped host sources (Tenable, Qualys, OpenVAS) write a raw export file to remediation/live-data/ — one more agent-driven step (/remediate <file>) is still needed before it appears on this dashboard's own pages, since classifying a host into one of 17 asset types needs judgment a script shouldn't guess at.
  • Already-normalized posture sources (Prisma Cloud, Cortex XSIAM) write straight to remediation/live-data/ as schema-ready findings — deliberately not auto-merged into the live queue.
  • Asset-inventory sources (Infoblox, Axonius, Active Directory) reconcile real ip/mac/hostname ground truth directly into the asset ownership store — an asset with no findings against it yet still won't appear on the Asset Inventory table until one does.
  • Push connectors (ServiceNow, Jira, Splunk) run in reverse: an Incident/Issue/Event is only created after you check the confirm box and submit — the preview above it is always free and makes zero network calls.
Two connectors with no admin walkthrough today

CrowdStrike Falcon is CLI-driven with a reference page only (/xdr) — no dashboard form yet. Armis is CLI-ingestion only. Both are real, working connector classes; neither has the Test Connection/Fetch UI described above.

Credentials: UI-entered, not environment variables — for every connector above

Some other parts of this app do read credentials from environment variables (SMTP, OIDC SSO, and the Active Directory group-membership check used by Remediation Approvals) — but none of the connector pages above work that way. Every one asks for real credentials fresh, in the browser, on every action (unless an admin stores the connection on the Connections page, §07). Don't confuse the Active Directory connector here (asset discovery, UI-entered LDAP bind credentials, its own /active-directory page) with that separately-configured, env-var-based AD group-validation check used elsewhere for approvals — genuinely different code paths against the same kind of directory.

05Rate limits & operational constraints

Real constraints from two directions: what each vendor's own API imposes on Quanta, and what Quanta itself does — or, honestly, doesn't yet — enforce on the way in.

Vendor-side: async jobs and pagination, not simple request caps

ConnectorReal constraint in the code today
Tenable.ioVulnerability export is Tenable's documented asynchronous job model: request an export, then poll GET /vulns/export/{uuid}/status every 5 seconds (default) until it reports FINISHED, up to a 600-second timeout before the connector gives up and raises. A large tenant's export can legitimately take several minutes — the Fetch button says so before you click it.
ArmisFollows Armis's real next pagination cursor, page by page (100 records per page by default), until the API returns no further cursor — capped at 100 pages as a self-imposed safety bound so an unexpected response shape can't loop forever, not a limit Armis itself documents.
OpenVAS/GVMSame async reasoning as Tenable's export: a real authenticated scan can run minutes to hours, so Start Scan/Check Status/Import Results are three separate calls (Vulnerability Finding Engine document, §03) instead of one blocking request.
Every other connectorA single request per action (test/fetch/send) — no pagination or async job, because the vendor's own API doesn't require one for these specific calls.

Quanta's own side — honestly incomplete, not silently assumed complete

No client-side retry/backoff in any vendor connector, and no explicit request timeout either

Only the CISA KEV/EPSS threat-intel client retries a dropped connection or timeout, with exponential backoff, up to 3 times — and that module is the only place in this codebase that sets an explicit HTTP timeout on its calls at all. None of the 13 named-vendor connectors in remediation/connectors/ do either: a transient network blip during a Tenable export or an Armis page fetch fails the whole action rather than self-healing, and a slow/hung vendor endpoint has nothing forcing it to give up. A real production deployment calling any of these connectors on a schedule should add the same retry-with-timeout pattern already proven in the threat-intel client, not assume it's already there.

Fixed: inbound rate-limiting now covers every connector route

This closes the gap the RBAC, Multi-Tenancy & Governance document's AI & security guardrails section also tracks: a real in-process, per-IP sliding-window rate limiter (dashboard/rate_limit.py) now sits in front of every /api/* route, including every connector's test/fetch/send route, with a stricter dedicated limit on the generic-ingestion webhook (POST /api/ingest/generic, §02 above) specifically — the sharpest edge outside production mode, where it takes no session or API key. Inbound API keys (§08) are additionally limited per key. This bounds call frequency; it does not cap how much data accumulates in total over time, which stays a real, disclosed follow-up. Single-node scope, disclosed plainly: each node counts independently, so a future multi-node deployment needs a shared store (e.g. Redis) instead.

07Credential handling — the one rule that never changes

Two modes, and which keeps nothing

Each connector's own page asks for credentials fresh on every action and persists nothing. The Connections page (admin only) is an explicit, opt-in alternative for scheduled syncs: credentials are encrypted at rest (Fernet) with QUANTA_ENCRYPTION_KEY, a key that lives outside the database. Without that key nothing is stored and the page says so. A stored credential is never returned by any API, a blank secret on edit keeps the stored one, backups never contain the key, and every run is audited. Supported for scheduled sync: Tenable, Qualys, Prisma Cloud, Cortex XSIAM, Infoblox, Axonius and Active Directory, plus the Anthropic and OpenAI usage connections (AI usage analytics, not findings). OpenVAS/GVM keeps its own start/status/import flow. Stored push connections: ServiceNow, Jira Cloud and Splunk HEC (§03).

Where the encryption key itself lives

In a Kubernetes or vault-backed deployment, QUANTA_ENCRYPTION_KEY and the other secrets are supplied as mounted files through the NAME_FILE convention (for example QUANTA_ENCRYPTION_KEY_FILE), never as environment variables. A key vault (Azure Key Vault, AWS Secrets Manager, GCP Secret Manager or HashiCorp Vault) feeds those files through External Secrets or the Secrets Store CSI driver. The Helm chart's secrets.mode is externalSecrets, csi, existingSecret or inline; inline is development only and refused unless secrets.allowInline is set. An explicit environment variable still wins over a file; a _FILE pointing at a missing or empty file stops the pod rather than starting with a random secret.

08Two directions: outbound and inbound

Everything above is outbound: Quanta calls a tool, using the vendor's own key. Inbound is the reverse: a tool, pipeline or person calls Quanta, using a Quanta-issued API key. A third path, file import, covers a source that cannot be reached by API. Machine-readable descriptions: GET /openapi.json (every route) and GET /api/connections/schema (every connection type as JSON Schema, admin only).

Push findings

curl -X POST https://quanta.example.com/api/ingest/findings \
  -H "Authorization: Bearer $QUANTA_KEY" -H "Content-Type: application/json" \
  -d '{
    "source": "my-scanner",
    "reconcile": false,
    "findings": [{
      "title": "OpenSSL heap overflow",
      "severity": "High",
      "asset": {"name": "web01", "ip": "10.0.0.5", "os": "Ubuntu 22.04"},
      "cve": "CVE-2024-1234", "cvss": 8.1,
      "source_ref": "scan-77-plugin-5120",
      "recommended_fix": "Upgrade openssl to 3.0.13"
    }]
  }'

Required: title, severity (Critical, High, Medium or Low; Moderate is accepted) and asset.name. Anything Quanta can work out (asset type, remediation domain, dates, KEV and EPSS) it does; unknown extra fields are ignored. A finding is identified by source + asset + source_ref (the title if omitted) + CVE, so sending it again updates it. Records are checked one at a time: a bad record is reported by index in errors and does not reject the rest. reconcile: true declares the request the complete current export for that source, so its findings missing from it are removed; a reconcile containing any invalid record is refused whole, so a partial export can never delete data. At most 5,000 findings per request.

Upload a scanner export

curl -X POST "https://quanta.example.com/api/ingest/scanner-csv?source=tenable-export&reconcile=true" \
  -H "Authorization: Bearer $QUANTA_KEY" --data-binary @export.csv

The body is the raw CSV in the Tenable column layout (Plugin ID, CVE, Risk, CVSS v3.0 Base Score, Host, IP Address, FQDN, OS, Name, Synopsis, Solution, Port, Protocol, First Discovered, Last Observed); Qualys and other scanners can export or be transformed to it.

Upload scanner results in SARIF

curl -X POST "https://quanta.example.com/api/ingest/sarif?source=semgrep&asset=shop-api&reconcile=true" \
  -H "Authorization: Bearer $QUANTA_KEY" --data-binary @semgrep.sarif

SARIF 2.1.0 is what Semgrep, CodeQL, OWASP ZAP, Trivy, Grype, Checkov, tfsec, KICS, gitleaks, Hadolint, actionlint and many others emit, so one endpoint covers SAST, DAST, SCA, secrets, IaC, container and pipeline findings without a connector per tool. Needs ingest:write. scan_type is worked out from the tool name (override with the query parameter), asset names the repository or application, and a finding keeps its identity through the tool's own fingerprint or a hash of rule, file and code (the line number is deliberately left out, so a moved line is not a new finding). reconcile=true declares the file the complete current result for that source. Severity comes from a numeric security-severity when supplied, otherwise the SARIF level (error High, warning Medium, note Low); Quanta does not raise a result to Critical on level alone. Suppressed results are skipped. The admin Import a scanner file button and quanta-admin import-sarif accept the same files. See the Vulnerability Finding Engine document for what is done with them.

Upload test coverage

curl -X POST "https://quanta.example.com/api/ingest/coverage?source=coverage&asset=shop-api&threshold=60" \
  -H "Authorization: Bearer $QUANTA_KEY" --data-binary @coverage.xml

Cobertura XML, JaCoCo XML or lcov. Only files whose path suggests security-relevant code and that fall below the threshold become findings; the response also gives the overall percentage. The path match is a heuristic on file names.

Report the security controls you observe

curl -X POST https://quanta.example.com/api/ingest/controls \
  -H "Authorization: Bearer $QUANTA_KEY" -H "Content-Type: application/json" \
  -d '{"source": "falcon", "controls": [
        {"asset_name": "WEB-*", "control_class": "edr", "name": "EDR, prevention on"},
        {"asset_name": "WIN-DC01", "control_class": "network-filtering", "name": "Perimeter firewall, deny by default"}]}'

Needs controls:write. An EDR, firewall or cloud-posture integration (or a script) tells Quanta which controls protect which assets; asset_name may be a glob such as WEB-* and control_class comes from a fixed vocabulary (GET /api/controls lists it). Controls reported this way are stored as verified; controls typed in or imported as CSV on the Controls page are claimed. This is what lets compensating-control advice be specific to your environment (see the Remediation Engine document).

Report AI usage

curl -X POST https://quanta.example.com/api/ingest/ai-usage \
  -H "Authorization: Bearer $QUANTA_KEY" -H "Content-Type: application/json" \
  -d '{"source": "gateway", "events": [{"ts": "2026-10-01T10:00:00Z", "model": "claude-sonnet", "provider": "anthropic",
        "team": "Platform Engineering", "application": "support-bot", "user_ref": "u-017",
        "input_tokens": 1200, "output_tokens": 300, "cache_read_tokens": 800, "event_key": "req-8841"}]}'

Needs ai-usage:write. Send an event_key (a request id) so a re-send updates instead of doubling, and a pseudonymous user_ref if people should not be identifiable. cost_usd is optional. Counts, models, times and attribution only.

OpenTelemetry (OTLP GenAI, JSON). Point an OTLP/HTTP exporter at POST /api/ingest/otlp/v1/traces with the same key and OTEL_EXPORTER_OTLP_PROTOCOL=http/json. Spans carrying the GenAI attributes (gen_ai.request.model, gen_ai.usage.input_tokens, gen_ai.usage.output_tokens) become events and service.name is the application; spans without a model or token count are ignored. The protobuf encoding is not read, and because the GenAI conventions are still evolving, both the older gen_ai.system and the newer gen_ai.provider.name are accepted.

Send SIEM or XDR alerts for triage

curl -X POST https://quanta.example.com/api/ingest/alerts \
  -H "Authorization: Bearer $QUANTA_KEY" -H "Content-Type: application/json" \
  -d '{"alerts": [{"external_id": "ALERT-1042", "source": "splunk", "title": "Shell spawned by w3wp.exe", "severity": "High",
       "asset": "WEB-1", "technique": "T1190", "occurred_at": "2026-10-02T09:14:00Z"}]}'

Needs soc:write. An alert is unique per source + external_id, so a re-send changes nothing. technique (an ATT&CK id) and asset are optional but are what let Quanta add vulnerability context when ranking the triage queue. Quanta never changes the alert's own severity and never decides an alert is real; this is intake for context and workflow, not a SIEM.

Report a ticket's state

curl -X POST https://quanta.example.com/api/inbound/ticket-status \
  -H "Authorization: Bearer $QUANTA_KEY" -H "Content-Type: application/json" \
  -d '{"finding_id": "FIND-42", "system": "servicenow", "state": "2", "external_ref": "INC0012345"}'

system is servicenow, jira or other. state is a ServiceNow number or word, a Jira status category or name, or one of open, in_progress, blocked, resolved. This is the push alternative to Quanta's own read-back polling in §03.

Read findings out

curl "https://quanta.example.com/api/export/findings?severity=critical&kev=true&limit=1000&offset=0" \
  -H "Authorization: Bearer $QUANTA_KEY"

Filters: source, severity, kev. Paged with limit (at most 5,000) and offset.

09Per vendor, end to end

  • ServiceNow. Create an integration user that can create and read incidents. Add a ServiceNow connection (instance name such as acme for acme.service-now.com, user, password, rule). Optionally add a business rule on incident that POSTs state changes to /api/inbound/ticket-status with a tickets:update key, using the finding id Quanta put in the incident's correlation_id.
  • Jira. Create an API token for a service account with create and browse rights in the project. Add a Jira connection (site URL, email, token, project key, rule). Issues carry the label quanta-<finding id>; state comes back by status category.
  • Splunk. Create an HTTP Event Collector token and add a Splunk connection with a rule. It is an append-only stream, so each finding is sent once.
  • Tenable and Qualys. Add the connection for a scheduled pull, or, if policy keeps scanner credentials out of other systems, have the scanner's own export job upload to /api/ingest/scanner-csv with an ingest:write key.
  • Prisma Cloud and Cortex XSIAM. Add the connection; findings arrive already in Quanta's schema.
  • Anything else (a SOAR playbook, an EDR, a custom collector). Post to /api/ingest/findings.
Verification status

Every connector is built against the vendor's public API and tested against simulated responses; none has been exercised against a live vendor account. Your first sync of each source is the live validation, and the disclosure on each connection's page says so.
