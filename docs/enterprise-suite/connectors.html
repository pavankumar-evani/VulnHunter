Connectors & Adaptors Catalog

One consolidated hub for every system VulnHunter can pull from, push to, or scan directly — organized honestly by what's actually working versus what's researched and ready to build next.

01The Adaptors hub

Every connector below is a risk-management decision, not just a technical integration — this is the only way real vulnerability, asset, and threat data enters VulnHunter's pipeline at all. The seven-stage remediation lifecycle (documented in the Remediation Engine & Workflows document) only ever sees what a connected source actually reported: an unconnected scanner, an unconfigured CNAPP, or an asset-discovery source nobody wired up is a coverage gap in your risk picture, not a limitation of the scoring or planning logic downstream of it. How current and complete that picture is — and how much the KEV/EPSS-aware prioritization described in the Vulnerability Finding Engine document is protecting against real, live threats rather than a stale snapshot — depends entirely on which of the sources below are actually connected in your environment.

Every integration lives in one place (/adaptors), filterable by category, with a two-tier honesty label instead of a single "supported" checkmark:

live

A real, working connector class + a real dashboard page — Test Connection, Fetch/Send, or (for the scan engine) the full scan lifecycle.

reference

Real, researched facts about the vendor's actual API — auth model, real endpoint shape, what data would flow — with no working code behind it yet.

A fourth path: findings pushed in, not pulled out

remediation/connectors/generic_connector.py is a different shape from every connector above — the receiving side of a webhook, for any SIEM/XDR/EDR/SOAR tool that already supports posting a custom outbound webhook. VulnHunter never calls out; the outside tool calls POST /api/ingest/generic with a JSON body validated against a minimal required shape (title, severity, asset_name, asset_type) and normalized into the same Finding schema every other source uses. One real, generic, testable adapter instead of another bespoke vendor connector nobody has real API access to verify.

Deliberately unauthenticated today

Unlike every connector above, this route is not gated behind rbac.require_admin or any session — a machine-to-machine webhook receiver, not something a logged-in browser session submits. That also means there is no cap on call frequency or on how large the resulting remediation/live-data/generic-ingested.json can grow. A real deployment needs a webhook-specific API key or HMAC signature, plus request throttling, in front of this route — a disclosed, real gap, not implemented here (see §05 below).

04Connecting a source — the admin walkthrough

This is the real, current path for an admin turning on an already-built source — not a developer wiring up a brand-new connector class (see the Developer Guide document's connector contract for that). All 11 connector pages with a real form — the 8 Test Connection/Fetch pages above plus ServiceNow/Jira/Splunk — follow the exact same shape:

StepWhat actually happens
1 · Open the connector's pageFrom /adaptors filtered by category, or directly (e.g. /tenable, /servicenow). Every real action below requires being logged in as admin — enforced server-side by rbac.require_admin, not just a hidden button.
2 · Enter credentialsDirectly into that page's form — e.g. Tenable's access key + secret key, generated from the vendor's own console. Typed fresh every visit; nothing is saved server-side, and there is no vault or "saved connection" anywhere in this catalog.
3 · Test ConnectionOne click, no confirm checkbox needed. Calls the vendor's cheapest real authenticated endpoint — Tenable's is GET /session, its lightest documented call — so a bad credential pair fails in under a second, before anything slower runs.
4 · Check the confirm box, then Fetch (or Send)The real action: a live export, scan, or send. Gated behind an explicit checkbox because it's a real call against a real production system — every push connector additionally shows you the exact payload for free before this step.
5 · See what landedDiffers by source category — see below.

Where the data actually goes

What "Fetch" produces depends on which source category a connector belongs to (full detail in the Vulnerability Finding Engine document's source taxonomy, §01):

  • CVE-scoped host sources (Tenable, Qualys, OpenVAS) write a raw export file to remediation/live-data/ — one more agent-driven step (/remediate <file>) is still needed before it appears on this dashboard's own pages, since classifying a host into one of 17 asset types needs judgment a script shouldn't guess at.
  • Already-normalized posture sources (Prisma Cloud, Cortex XSIAM) write straight to remediation/live-data/ as schema-ready findings — deliberately not auto-merged into the live queue.
  • Asset-inventory sources (Infoblox, Axonius, Active Directory) reconcile real ip/mac/hostname ground truth directly into the asset ownership store — an asset with no findings against it yet still won't appear on the Asset Inventory table until one does.
  • Push connectors (ServiceNow, Jira, Splunk) run in reverse: an Incident/Issue/Event is only created after you check the confirm box and submit — the preview above it is always free and makes zero network calls.
Two connectors with no admin walkthrough today

CrowdStrike Falcon is CLI-driven with a reference page only (/xdr) — no dashboard form yet. Armis is CLI-ingestion only. Both are real, working connector classes; neither has the Test Connection/Fetch UI described above.

Credentials: UI-entered, not environment variables — for every connector above

Some other parts of this app do read credentials from environment variables (SMTP, OIDC SSO, and the Active Directory group-membership check used by Remediation Approvals) — but none of the connector pages above work that way. Every one asks for real credentials fresh, in the browser, on every action. Don't confuse the Active Directory connector here (asset discovery, UI-entered LDAP bind credentials, its own /active-directory page) with that separately-configured, env-var-based AD group-validation check used elsewhere for approvals — genuinely different code paths against the same kind of directory.

05Rate limits & operational constraints

Real constraints from two directions: what each vendor's own API imposes on VulnHunter, and what VulnHunter itself does — or, honestly, doesn't yet — enforce on the way in.

Vendor-side: async jobs and pagination, not simple request caps

ConnectorReal constraint in the code today
Tenable.ioVulnerability export is Tenable's documented asynchronous job model: request an export, then poll GET /vulns/export/{uuid}/status every 5 seconds (default) until it reports FINISHED, up to a 600-second timeout before the connector gives up and raises. A large tenant's export can legitimately take several minutes — the Fetch button says so before you click it.
ArmisFollows Armis's real next pagination cursor, page by page (100 records per page by default), until the API returns no further cursor — capped at 100 pages as a self-imposed safety bound so an unexpected response shape can't loop forever, not a limit Armis itself documents.
OpenVAS/GVMSame async reasoning as Tenable's export: a real authenticated scan can run minutes to hours, so Start Scan/Check Status/Import Results are three separate calls (Vulnerability Finding Engine document, §03) instead of one blocking request.
Every other connectorA single request per action (test/fetch/send) — no pagination or async job, because the vendor's own API doesn't require one for these specific calls.

VulnHunter's own side — honestly incomplete, not silently assumed complete

No client-side retry/backoff in any vendor connector, and no explicit request timeout either

Only the CISA KEV/EPSS threat-intel client retries a dropped connection or timeout, with exponential backoff, up to 3 times — and that module is the only place in this codebase that sets an explicit HTTP timeout on its calls at all. None of the 13 named-vendor connectors in remediation/connectors/ do either: a transient network blip during a Tenable export or an Armis page fetch fails the whole action rather than self-healing, and a slow/hung vendor endpoint has nothing forcing it to give up. A real production deployment calling any of these connectors on a schedule should add the same retry-with-timeout pattern already proven in the threat-intel client, not assume it's already there.

Fixed: inbound rate-limiting now covers every connector route

This closes the gap the RBAC, Multi-Tenancy & Governance document's AI & security guardrails section also tracks: a real in-process, per-IP sliding-window rate limiter (dashboard/rate_limit.py) now sits in front of every /api/* route, including every connector's test/fetch/send route, with a stricter dedicated limit on the generic-ingestion webhook (POST /api/ingest/generic, §02 above) specifically — still the sharpest edge, since it takes no session or API key at all. This bounds call frequency; it does not cap how much data accumulates in total over time, which stays a real, disclosed follow-up. Single-node scope, disclosed plainly: each node counts independently, so a future multi-node deployment needs a shared store (e.g. Redis) instead.

Why not just build all of them

The connector pattern is proven; adding another named product is "the same pattern again, gated on picking one and having real API access to verify against" — not a capability gap. Shipping a plausible-looking connector nobody has run against a real account isn't a shortcut worth taking.

07Credential handling — the one rule that never changes

Per-request, never stored, no exceptions

Every connector page asks for real credentials fresh, on every Test Connection or Fetch/Send/Scan action. Nothing is persisted server-side. There is no vault, no saved-connection list, no "remember this account" option anywhere in this catalog.
