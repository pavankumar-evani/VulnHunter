Remediation Engine & Workflows

From a scored finding to a reviewable, human-approved fix artifact — every real stage, who or what performs it, and the one boundary this engine will never cross on its own.

01The seven-stage lifecycle

Detection is covered in the Vulnerability Finding Engine document. This picks up once a finding is scored and continues through to a human decision.

1
Automatic

Plan

remediation-planner assigns an action type, the automation mechanism that could handle it, a risk tier, and a rollback plan — written to REMEDIATION_PLAN.md.

2
Automatic, once eligible

Generate

remediation-fixer-windows/-unix/-ot/-application drafts a real artifact — an Ansible playbook, a compensating-control recommendation, or a dependency-upgrade plan, depending on domain (see §07) — for windows-server/unix-server/iot-ot-device/application findings, the four asset types with a working fixer today.

3
Human

Review

Open the playbook, read its header (finding ID, risk tier, rollback instruction), honor a CHANGE APPROVAL REQUIRED comment if present, verify anything the fixer explicitly declined to guess.

4
Human, recorded

Request approval

A remediation-approvals request is created against the next real maintenance window from the resolved remediation policy (§5).

5
Human (admin)

Approve or reject

Recorded with who decided, when, and (if AD is configured) whether the approver's group membership was verified. A pending request past its window with no decision auto-reports as expired.

6
Human, one click

Trigger

Marks the approval remediation_triggered — the honest ceiling of what this app tracks. Not independent confirmation the fix was applied.

7
Outside this app, always

Apply

Run by a person or your org's own change-managed automation platform (Ansible Tower/AWX, SCCM, Intune). Quanta performs this step in zero cases.

02Planning & risk tiering

Two scoring mechanisms exist side by side, deliberately:

REMEDIATION_PLAN.md

A point-in-time snapshot written once per pipeline run — the artifact a change-management process can attach to a ticket.

Live priority engine

Re-scores every finding on every dashboard load from the current priority_rules.yaml — what an admin editing SLA weights actually sees change, in real time.

Risk tier defaults conservative: needs-change-approval is chosen over auto-approvable whenever the planner is uncertain, even when the underlying fix is mechanical. KEV/EPSS threat intel never overrides risk tier — only priority. An actively-exploited CVE on a domain controller is still needs-change-approval; it's just more urgent to get that approval.

03Playbook generation

Every generated playbook carries the same real header discipline:

Header elementPurpose
Finding ID + risk tierTraceable back to exactly one scored finding
Rollback commentA real, human-written rollback procedure (ISO/IEC 27002:2022 §8.32-aligned) for this specific fix
Pre-change state checkConfirms the target's current state before making any change
# CHANGE APPROVAL REQUIREDPresent whenever risk tier is needs-change-approval — a visible gate inside the artifact itself, not only in the workflow around it

04Approvals vs. exceptions — two different decisions

Remediation Approval

"Yes, proceed with this fix" — a real request against a real maintenance window, decided by an admin, tracked to pending / approved / rejected / expired / remediation_triggered.

Exception

"Accept this risk instead of fixing it" — a time-boxed record (active / expired / revoked) that suppresses SLA pressure on a specific finding without ever generating a playbook for it.

05Remediation policy engine

Resolved live on every dashboard load from remediation/config/remediation_policy.yaml, per one of 18 asset domains: change type, cadence, maintenance window, whether auto-remediation is even permitted for that domain, the required approval group, and which PAM backend a playbook's credential lookup should target at run time.

The one hardcoded override

A KEV-listed finding always escalates its policy to change_type: emergency — regardless of what the domain's own configured cadence says. This is deliberate, not a bug: an actively-exploited vulnerability doesn't wait for the next scheduled window.

06The execution boundary

Verbatim — this is the load-bearing sentence in this entire engine

"Nothing in this repository ever executes against real infrastructure automatically — by construction, not by policy." The fixer subagents hold Read, Write tool access only — no Bash, no network tool, no stored credentials. They cannot reach a host even if instructed to. PAM/Vault integration is a lookup-plugin snippet resolved by your infrastructure at playbook-run time — Quanta never holds a live secret.

07Four remediation tracks — deliberately not one workflow

Everything above describes the IT-infrastructure track in detail. Quanta actually runs four genuinely separate remediation mechanisms, each shaped for how that category of finding is really fixed in practice — not one generic "generate a fix" pipeline stretched to cover cases it doesn't fit.

Why AppSec (SAST) was never merged into the infra track

vuln-fixer edits source files directly and opens a pull request — a fundamentally different action than generating a standalone playbook for someone else to run. It has its own tool scope (Bash for git, Edit for source files) and its own trigger (/quanta-scan --fix), independent of /remediate's pipeline entirely. DAST, Secrets, and Container findings don't have an equivalent fixer yet — they're honestly manual-only today, the same disclosed gap as network devices and certificates.

Why OT gets a different artifact shape, not just a different template

NIST SP 800-82 (OT security guidance) treats direct automated patching as the exception in industrial environments, not the default — many OT devices can't be safely rebooted mid-production, some have no reachable network path at all, and an unplanned change to a safety-critical controller risks physical harm, not just downtime. remediation-fixer-ot reflects that directly: it never generates a config/patch script, only a recommendation for IT security and OT/plant operations to act on together.

Why the SCA fixer follows the Ansible pattern, not vuln-fixer's

remediation-fixer-application has only Read, Write tools — no Bash, no git access — unlike vuln-fixer. A dependency bump's real risk is a transitive breaking change this subagent has no way to test (no build tooling, no test suite), so it generates the upgrade plan a developer executes through their own normal PR workflow, the same artifact-only posture as the Ansible/OT fixers, not a diff pretending to already be validated.

Closing the loop: post-fix verification

Only the SAST track has this today: vuln-verifier (part of the Vulnerability Finding Engine document's /quanta-scan pipeline, triggered by --verify FINDING-ID BRANCH) re-checks a fixed finding against its fix branch from a fresh read and logs a real resolved/still-present/inconclusive verdict — closing the gap where a fixer's own report was previously the only signal a fix worked. The three /remediate-side tracks don't have an equivalent re-check yet.

08Safety gates, staged rollout and proof

Three deterministic layers wrap the model-written fixers, so a reviewer gets a mechanical answer before they are asked to decide.

Playbook safety lint

Every generated playbook is checked for a named finding, a stated risk tier, a real rollback procedure, the change-approval gate where the tier requires it, valid YAML structure, no literal credentials and no hosts: all. Warnings flag a missing pre-change check, a missing post-change verification, raw shell use and silenced failures. An approval is refused while any error stands.

Staged rollout rings

The remediation policy resolves a ring plan per finding: canary, pilot, then broad, with a soak period between rings (an emergency profile for actively exploited findings). Generated playbooks take a rollout_ring variable so no single run can touch every host. Quanta still executes nothing; whoever runs the playbook honors the rings.

Closed-loop verification

After a remediation is triggered, the next scan decides: verified (no longer reported), still present, or awaiting rescan. "Verified" is evidence, not proof, because an asset leaving scan scope looks the same, and the interface says so.

Evidence and metrics

An evidence pack bundles the finding, the approval trail, the reviewed artifact with its lint result and the outcome. Outcome metrics report real request-to-approval and request-to-trigger times and the fix-hold rate, and return no value rather than an estimate when there is no data.

09Analyst guidance and its limits

Alongside the generated artifacts, every finding carries written, step-by-step guidance for the person who has to fix it. It changes nothing itself.

Curated knowledge base

remediation/guidance/knowledge.yaml is a human-written, editable set of 29 entries (injection, XSS, access control, secrets, crypto, dependencies, containers, IaC, CI/CD, OS patching, network, OT/IoT, cloud, AI/ML, end-of-life and more) plus a generic fallback. Each has a summary, why it matters, ordered steps, how to confirm the fix, compensating controls if it cannot be fixed now, effort and references (OWASP, CIS, NIST, CISA, SLSA, CWE).

Matching and tailoring

A finding is matched by CWE, then scan type, asset type and keywords, and the guidance says why it matched. It is tailored from known facts: dependency package and fixed version with the typical upgrade command, Windows KB with a check command, CISA KEV listing and due date, high EPSS, a breached SLA, and the scanner's own recommendation (hidden when it is only "See vendor advisory"). It also states what Quanta can automate for the finding, or that it can automate nothing.

Honest limits

Coverage is curated for common classes, not every CWE; unmatched findings get the generic approach, labelled generic. The guidance is curated knowledge, not generated by a model, so it reads the same on every run and your own team can edit it. Client-specific compensating controls are assessed against the controls inventory (see §10); until an asset has controls recorded, the guidance says its controls are general and how to record them. It appears in the finding detail modal and on the Code Scan page.

10Client-specific compensating controls

For a finding that cannot be fixed yet, the useful question is what should be in place so the flaw is hard to use, and what already is. remediation/enrichment/client_controls.py answers it in three checkable steps, and the result appears in the finding guidance (/api/findings/{id}/compensating-controls).

1 · Techniques the flaw enables

From the finding's tagged ATT&CK techniques and, for code and web findings, its CWE ids (a CWE-to-technique mapping ships in attack_mitigations.yaml). The technique tagging is the same keyword heuristic documented in the Vulnerability Finding Engine document, so it is a rough grouping, not attribution.

2 · MITRE's mitigations

attack_mitigations.yaml holds the mitigations MITRE publishes on attack.mitre.org for every technique Quanta tags, each expressed as a control class that can be checked for (EDR, network filtering, MFA, least privilege, audit logging and others), plus indicative NIST 800-53 mappings. A technique MITRE lists no mitigations for (T1600) yields none, and the result says so.

3 · What the asset has

Each mitigation is checked against the controls inventory (remediation/controls/store.py, table asset_controls, asset names may be globs such as WEB-*): verified (an integration reported it, via POST /api/ingest/controls with a controls:write key), claimed (a person typed or imported it), absent (the asset has recorded controls but not this one, which is a gap to close) or unknown (nothing is recorded for the asset at all).

Coverage is a simple disclosed measure: of the applicable compensating mitigations, a verified one counts 1 and a claimed one counts 0.5. Patching and scanning are shown separately because they are the fix, not a compensating control. The same inventory feeds the threat-model residual score.

Unknown means unknown

With nothing recorded for an asset, Quanta says unknown and gives general advice rather than guessing that a control is or is not there. The inventory ships empty, and "verified" means a connector or script reported it, not that Quanta tested it. Coverage is indicative, not a risk calculation, and no firewall, EDR or posture connector has been exercised against a live vendor tenant.

11GRC evidence, as it relates to remediation

Remediation produces facts a compliance program needs: how fast findings are fixed, whether SLAs are met, whether fixes were approved and verified. The GRC module (remediation/grc/, admin only) turns those facts into evidence against a framework's controls. Quanta supplies evidence and workflow; it does not certify compliance or give an audit opinion.

Automated control tests

evidence.py runs tests whose thresholds and test-to-control mappings live in remediation/config/grc_tests.yaml, collected hourly by the leader's scheduler tick. Where there is too little data, the result is na, never a pass. Frameworks are built-in subset catalogs (NIST 800-53 r5, CSF 2.0 and an AI-governance set) or a full catalog imported as OSCAL JSON.

Attestations, risks and export

Attestations (a person's recorded statement about a control) sit beside the evidence rather than replacing it. A risk register with likelihood x impact grids takes suggestions from live findings and threat models. report.py gives per-control status and an OSCAL assessment-results export that records what Quanta observed; validate it with NIST's OSCAL tooling before relying on it.

The built-in catalogs are subsets, not complete frameworks, and the control mappings are indicative. An auditor remains the party who decides whether a control is satisfied.

12Hunting and SOC triage: the detect counterpart

Remediation closes exposure; hunting asks whether the exposure was used before it was closed. The two share the same data, and neither replaces the other.

From a KEV finding to a hunt

An open CVE that is on the KEV list, or has an EPSS score of at least 0.5, becomes a hunt with the affected hosts, the ATT&CK techniques tagged on those findings and a query per detection, rendered as Splunk SPL. The analyst runs it in their own tool and records the result. Closing a hunt requires an outcome.

Alert triage with vulnerability context

Alerts sent to POST /api/ingest/alerts are ranked by severity plus what Quanta knows about the host (open KEV findings, a finding matching the alert's technique, high EPSS, no recorded owner), with a runbook attached. It reorders a queue; it never changes an alert's severity or decides that it is real.

Not a SIEM

Quanta does not run hunt queries, collect logs or detect intrusions. Its Splunk push connector sends findings out; the hunt queries are text for an analyst to run.

13What is not built

Stated plainly, so nothing above is read as more than it is.
